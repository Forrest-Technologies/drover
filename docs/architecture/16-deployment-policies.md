# 16. Deployment policies

Drover is built for self-hosting first. When the owner later runs it as a service for other people, the same build is switched into a stricter mode by policy, not by a fork and not by scattered `if (hosted)` checks.

## The idea

A **deployment policy** is a set of named rules the operator sets when the server starts. Each rule either allows something, forbids it, or caps it. Feature code never asks "am I hosted?". It asks the policy a specific question: "may this server call a private address?", "is this sign-in adapter enabled?".

Two presets ship:

| Preset | For | Character |
| --- | --- | --- |
| `self_hosted` (default) | One person or household on their own machine | Permissive. The operator is trusted and is usually the only user. |
| `hosted` | A service run for strangers | Every rule at its strict value, except the few permissions the owner has decided stay on because other rules bound them (below), and **locked**: no setting in the UI, a space, or a bot can loosen it. |

The operator picks a preset with one setting, `DROVER_POLICY`, and may tighten individual rules beyond it. Loosening a rule below the `hosted` preset is not possible while that preset is selected; the server refuses to start and says which rule.

## Limits only narrow

The same principle as the bot tree, applied to configuration:

```
deployment policy   (operator, at start)
   └─ space policy  (space owners and admins)
        └─ bot settings
```

Each level can restrict what the level above allows and can never widen it. A space can forbid untrusted MCP servers that the deployment allows; it cannot enable a sandbox adapter the deployment forbids. The effective value is computed in one place, `PolicyService`, and is what the engine, the API, and the UI all read.

## Rules

Collected from the rest of this document. Each is a typed property on the `DeploymentPolicy` record.

| Rule | `self_hosted` | `hosted` | Why it exists |
| --- | --- | --- | --- |
| Outbound requests to private and link-local addresses (model base URLs, MCP URLs, OAuth discovery) | Allowed | Forbidden | Stops a tenant aiming the server at internal systems. Local models and LAN servers are normal when self-hosting. |
| Sandbox adapters available | All | Only those with a hard isolation boundary; the Docker adapter is off | Plain containers are not a boundary between strangers |
| Sandbox limits: command time, file size, idle time before pausing | Generous | Tighter | A running sandbox costs the operator money whether it is used or not |
| Sandbox open internet access | Allowed | Forbidden; off and named hosts only | Under the operator's provider account, what a stranger's sandbox does on the open internet is the operator's liability |
| Sandboxes with a screen (computer use) | Allowed | Forbidden | A desktop sandbox is a far larger machine; until per-space quotas exist, nothing bounds what it costs the operator |
| Bots making and managing the bots beneath them (crew tools) | Allowed | Allowed, by the owner's decision | Bounded instead of forbidden: every path that makes a bot counts against the space's cap on its bots (`MaxBotsPerSpace`, narrowed by the space's `max_bots`), and making a bot always waits for a person, whatever `crew.add` is set to |
| How many bots one space may hold | 1000 | 100 | Each is a row on the operator's database and a bot that can be run |
| Schedules: the shortest time between two runs of one, and how many one space may hold | Every minute; 1000 | Every 15 minutes; 100 | Each time a schedule comes due is a run on the operator's server and the space's model credit that nobody is watching |
| A run tree's delegation budget: how deep a chain of bots may go, how many runs one tree may hold, and what it may cost before no further delegation begins | 5 levels, 50 runs, 100.00 | 5 levels, 50 runs, 10.00 | A chain of bots handing work on is where a runaway loop spends a person's model credit with nobody watching each step |
| Local-process (stdio) MCP servers | Inside a sandbox only | Inside a sandbox only | Never on the host, in any mode |
| Subscription sign-in adapters, per provider | On where the provider permits self-hosted use | Off unless the operator has that provider's approval for hosted use, recorded per provider | Provider terms differ for hosted apps |
| Model providers available | All | A list the operator sets, after reading each provider's terms for hosted use | Same |
| Open registration (`OpenRegistration`) | Off after the first account; the operator may turn it on only with private addresses forbidden | Off; the operator may turn it on, and then email verification and acceptance of terms are required | Abuse control. Everyone who registers owns a space and can add connections, so on a server that allows private addresses a stranger could aim it at the database, the container gateway, or a cloud metadata address. |
| Acceptance of terms of service and privacy notice at sign-up | Off | Required, with the version accepted recorded | Legal, and some providers require their terms to flow down to end users |
| First-run setup code (`RequireSetupCode`) | Required for every request | Required for every request; provisioning is the operator's, so the screen is rarely used | Prevents claiming an empty server. No address proves a request is local, because a proxy or tunnel on the same host makes a remote request look local. |
| Per-space quotas: runs per day, concurrent runs, storage, sandbox minutes (the number of bots is capped by its own rule, above) | Unlimited by default | Set by plan | Fair use and cost |
| Tainted-run escalation ([06-mcp.md](06-mcp.md)) | On, a space may turn it off per bot | On, cannot be turned off | Limits what a hostile tool result can cause |
| Remote images in bot output load automatically | Off, a space may turn it on | Off, cannot be turned on | Data can leak through an image address |
| Key ring protection | File permissions | A certificate or key service is required; the server refuses to start without one | A database dump must not be enough to read secrets |
| Migration credential in the serving process | Allowed (single container) | Forbidden; migration is a separate job | Least privilege |
| Audit log retention and export | Operator's choice | Minimum retention enforced | Accountability |
| Data export and account deletion endpoints | Available | Available and cannot be disabled | Users' rights |
| Telemetry export | Off unless an endpoint is set | Operator's endpoint; message content never included in any mode | Operations |
| Operator access to tenant content | Not applicable | None through the product. Support access, if ever added, is an explicit, audited, time-limited grant from the space owner | Trust |
| How long one note a bot keeps about a person may be, and how much its notes about one person may hold together | 1,000 characters; 20,000 characters | 500 characters; 8,000 characters | Every run of the bot for that person is given all of its notes, so this bounds what memory adds to every model call the person's runs make, and on a shared server the rows one person's bot can write. A bot's own setting may only lower it |
| Bots searching the web and reading pages by address (`web.search`, `web.fetch`), and how much and how long one read may take | Allowed; 4 MB and 30 seconds | Forbidden; 1 MB and 15 seconds | Every search and page is a request from the operator's server, on the operator's address, made for a stranger. A page is never read from a private, loopback, or link-local address in any mode |
| Running summaries of main conversations, and how long one summary's model call may take | On; up to 120 seconds | On, by the owner's decision; up to 60 seconds | The call is made on the server's own initiative after a run, spends the space's model credit, and holds a run worker while it lasts, so on a shared server a slow model must not keep other people's runs waiting. It is bounded by what a person does: a summary is due only once 20 new person and bot messages lie beyond the last one, so there are never more summaries than runs people start, each reads at most 200 messages of at most 4,000 characters and writes at most 1,000 tokens, and each call is cut off at the time limit |

A new feature that could harm other tenants, cost the operator money without limit, or break a provider's terms on a shared server ships with a rule here.

`OpenRegistration` is the one rule the operator of a hosted service may loosen: the table's "operator's choice". Every other rule is locked to its preset.

The hosted preset sets every locked rule to its strictest value, with one kind of exception: a permission the owner has decided stays on in the hosted preset because other rules bound what it could cost. Such a rule is marked `IsAllowedWhenHosted` in the rule table, and today there are two, `AllowBotsBuildingBots` and `AllowConversationSummaries`. It is still locked, so an operator may turn it off and no space can turn it back on. `DeploymentPolicyTests` checks that every other locked rule is at its strictest in the hosted preset, so a rule left loose there by accident still fails the build, and that the marked rules are exactly those two; marking another is a decision that changes that test. The sign-in rate limit, the key ring path, and quota amounts are configuration, not rules.

## Mechanics

| Piece | Design |
| --- | --- |
| Type | `DeploymentPolicy`, a record in `Drover.Domain` with one typed property per rule. No string keys in feature code. `DeploymentPolicy.Rules` is the table of rules (name, value, how loose it is, where it is enforced). |
| Presets | Two static values, `DeploymentPolicy.SelfHosted` and `DeploymentPolicy.Hosted`, the second built from the first with extension methods in the guide's builder style (`AsHosted`) |
| Loading | `DeploymentPolicySetup` in `Drover.Server` builds `DeploymentPolicyOptions` through the platform's options system. `DROVER_POLICY` (or `Drover:Policy:Preset`) names the preset, `Drover:Policy:Rules:<Rule>` tightens one rule, and `Drover:Policy:TermsVersion` names the terms people accept. It is validated when the host starts: a rule set looser than the preset, a key that names no rule, an unknown preset, an enum rule whose number is not one of its values, a hosted server without a key ring certificate, a migration credential (`ConnectionStrings:DroverOwner`, or `Database:Password`, `Database:OwnerPassword` or their `File` forms) in a server that forbids it (where it is allowed, the server uses `Database:OwnerPassword` and `Database:Password` to apply its own migrations at start and logs an error only for a setting it does not use), open registration that asks for terms with no version, or open registration while private addresses are allowed stops the server. Where the migration credential is forbidden, the server also asks the database who the request connection is at start (`DatabaseRoleGuard`) and refuses unless it is `drover_app` with no superuser or row-level-security bypass. Each requirement is checked when the preset asks for the strict value, whatever the configured value is. Each refusal names the rule. |
| Reading | `PolicyService` in `Drover.Engine` returns the effective value for a space: the deployment rule narrowed by the space's settings. It is the only place that computes one. |
| Space policy | Stored in `spaces.settings` (`SpaceSettings`), restricted to rules a space may narrow: `AllowPrivateAddresses`, `TaintedRunEscalation`, `AutoLoadRemoteImages`. A space can forbid private addresses; it cannot allow them where the deployment forbids. It can turn off tainted-run escalation or turn on remote images only where the deployment rule says a space may. Bot settings do not narrow policy yet. |
| Enforcement | At the point of action, on the server: `OutboundHttp` (below), `POST /api/setup`, `POST /api/register`, and server start. Sandbox provider registration and the sandbox broker are enforcement points too. Never only in the UI. |
| Outbound requests | `OutboundHttp.CreateHandler` is the primary handler of every `IHttpClientFactory` client (set once with `ConfigureHttpClientDefaults`). A request may reach a private address only when the deployment allows it and the request says so: the caller puts the space's effective value on the request with `ForSpace`, and a request that says nothing is treated as forbidden. A request to an address the operator configured for the whole server, which no space, person, or bot can change (today the search service of `web.search`), says so with `ForOperatorAddress` (`OperatorAddressHandler` on that client), and may reach a private address whenever the deployment allows private addresses. `web.fetch` reads pages through a client that never says anything, so a page is refused a private address in every mode. Model provider adapters build their own requests, so `SpaceOutboundHandler` (added to their named clients) copies the space's value from the surrounding `OutboundAttempt` onto each request ([15-model-providers.md](15-model-providers.md)). A refusal is raised as `OutboundBlockedException` (in `Drover.Domain`, so adapters can see it). The adapters never retry it and never count it toward their per-host circuit breaker, because one space's refusal says nothing about the provider and a shared host must not pause for it; it reaches the person as a rejected connection with the refusal's own message. Forbidden requests resolve the host, are refused if any returned address is private, link-local, loopback, shared, IPv4-mapped, or a NAT64/6to4 form of one, and connect to the address they checked, so the answer cannot change between check and connect. The check runs on every new connection, so a redirect to another host is checked again. Allowed and forbidden requests use separate connection pools. HTTP/3 is refused, since it skips the connection check, and a request is not left free to upgrade to it. A guarded request does not use an outbound proxy. `BannedSymbols.txt` bans `new HttpClient(...)`, `SocketsHttpHandler` and `HttpClientHandler` construction. Only the policy code, its handler tests, and the web page reader's tests (which build its client on the handler with a test's address lookup) are exempt on the server. The web and Android client hosts are also exempt (in `.editorconfig`); they send requests to their Drover server and never run in the server process. |
| Visibility | `GET /api/status` (signed-in people) lists the active preset and every rule with its setting and where it is enforced. The UI hides or explains what a rule forbids: "Not available on this server." |
| Tests | `DeploymentPolicyTests` in `Drover.Domain.Tests` checks that the hosted preset is never looser than the self-hosted one and is at its strictest for every locked rule not marked `IsAllowedWhenHosted`. `PolicyMatrix` in `Drover.Server.Tests` has a row per rule, and `PolicyMatrix.Refusals` a row per combination the server refuses at start (today: open registration with private addresses allowed); `PolicyStartupTests` starts the server with each and checks the refusal names every setting to change. A test fails when a property of `DeploymentPolicy` has no row, and the matrix tests start the server under each preset and check the status listing and each enforced rule. `PolicyServiceTests` in `Drover.Engine.Tests` covers narrowing, including that a space cannot loosen. A source scan in `Drover.Domain.Tests` fails on a source file outside the policy types that names or compares a preset. |

`hosted` is a preset, not a separate product. Everything it does is in the open source repository and a self-hoster running a server for their community can select it too.

## What this is not

- **Not billing.** Plans and payment for the hosted service are outside the open source server. They set quota values through the same space policy any operator can set.
- **Not a feature flag system.** Rules exist to restrict for safety, cost, or compliance. A feature that is simply unfinished is not shipped.
- **Not a replacement for row-level security.** Tenant isolation is on in every mode and has no rule to turn it off.

## Phase

Phase 0 builds the type, the two presets, loading, the status listing, and the matrix test, with the rules that already have something to guard: outbound address checks, the setup code, registration and acceptance of terms, the migration credential, and key ring protection. Each later feature adds its own rule when it is built.

Two things are not done yet: the server cannot send the email that email verification needs, so `POST /api/register` answers 501 where verification is required; and it does not read forwarded headers, so per-address rate limits and the "same machine" check see the proxy's address.
