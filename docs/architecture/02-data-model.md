# 2. Core data model

PostgreSQL, one schema `public` for tenant data and one schema `sys` for the audited cross-tenant functions. Names are `snake_case`. Primary keys are UUID version 7 (`Guid.CreateVersion7()`), which sort by creation time and need no coordination.

## Ownership classes

Every table belongs to exactly one class. The class decides its row-level security policy ([04-tenancy-and-permissions.md](04-tenancy-and-permissions.md)).

| Class | Marker in C# | Column | Policy |
| --- | --- | --- | --- |
| Space-owned | `ISpaceOwned` | `space_id uuid not null` | Row visible and writable only when `space_id` equals the transaction's space |
| Space-owned with an audience | `ISpaceOwned, IAudienceScoped` | plus `audience_user_id uuid not null` | As above, and the audience is "everyone in the space" or equals the transaction's user |
| User-owned | `IUserOwned` | `user_id uuid not null` | Row visible only to that user |
| Global | listed in `GlobalTables.manifest` (`src/Drover.Data/`) | none | App role has no direct access, read-only reference data, or a policy written by hand and covered by a named test (`spaces`, `users`) |

Every foreign key between two space-owned tables is composite, `(space_id, x_id)` referencing `(space_id, id)`. A row therefore cannot point at another space's row even if application code tries. Foreign key checks are not subject to row-level security, so this closes a gap the policies alone leave open.

### Users, personal spaces, and shared spaces

Isolation between people is the normal case and the database enforces it at two levels.

| Level | What it is | Enforced by |
| --- | --- | --- |
| **Personal space** | Every user gets one at sign-up, with exactly one member. Their own bots, connections, threads, and secrets live here. | Space isolation. Another user is simply in a different space. |
| **Shared space** | A group that several users belong to. Bots, connections, and the bot tree are the group's. | Space isolation between groups, plus the audience column inside the group. |

Inside a shared space, each content row has an **audience**: one user, or everyone in the space. `audience_user_id` holds the user's id, or the all-zero UUID meaning everyone. A private thread, its messages, its run events, its tool calls, and its files are invisible to other members of the same space, by policy, not by application check.

The column is `not null` with a sentinel on purpose. It lets child tables carry the audience inside their foreign key, `(space_id, thread_id, audience_user_id)` referencing the thread with `ON UPDATE CASCADE`. The database then guarantees a message can never have a wider audience than its thread, and sharing a thread updates every descendant row in one statement. A nullable column cannot do this, because a null in a composite foreign key skips the check.

What is shared by the whole space, and has no audience column: bots, grants, connections' definitions, the tool catalog, and the `runs` and `usage_records` rows. A run row is metadata only (which bot, status, timing, cost). That lets space admins see activity and cost and cancel any run, while the content of a private thread stays unreadable to them.

## Bots

| Table | Class | Key columns |
| --- | --- | --- |
| `bots` | Space-owned | `id`, `parent_bot_id null`, `name`, `handle`, `avatar jsonb`, `description_for_bots`, `instructions`, `model_connection_id`, `model`, `model_settings jsonb`, `memory_settings jsonb`, `sandbox_policy`, `sandbox_settings jsonb`, `status`, `depth`, `build_limits jsonb`, `created_by_user_id null`, `created_by_bot_id null` |
| `bot_ancestors` | Space-owned | `ancestor_bot_id`, `descendant_bot_id`, `distance` |
| `bot_sandbox_shares` | Space-owned | `bot_id`, `shared_with_bot_id` |
| `bot_schedules` | Space-owned | `bot_id`, `owner_user_id`, `cron`, `time_zone`, `prompt`, `thread_mode`, `enabled`, `next_run_at`, `last_run_id null`, `last_run_at null`, `last_outcome null` |
| `tool_grants` | Space-owned | `bot_id`, `tool_id`, `effect`, `review_state`, `granted_by_user_id null`, `granted_by_bot_id null` |
| `bot_rules` | Space-owned | `id`, `bot_id`, `name`, `enabled`, `position`, `checkpoint`, `effect`, `conditions jsonb`, `created_by_user_id null` |

Notes:

- `status` is `active`, `paused`, or `removed`. A bot is effectively paused when it or any ancestor is paused.
- `sandbox_policy` is `none`, `private`, `subtree`, or `named`. A bot with a sandbox defaults to `private`.
- `build_limits` narrows the space caps for one bot: how many children it may create and how deep beneath itself.
- A person who may create bots (owner or admin) creates one at the top of the tree or beneath a parent of the same space that has not been removed. The parent row is locked while the child is added, so two additions count its children one after the other. The space caps `max_bot_depth` (the deepest a bot may sit, the top being 0) and `max_children_per_bot`, the parent's `build_limits.max_children`, and the `build_limits.max_depth_below` of the parent and of every bot above it each refuse the request in words when they would be exceeded; a cap left empty does not limit, and removed children do not count. `max_bots` caps the bots of the space that have not been removed, on every path that makes one (created at the top or beneath a parent, duplicated, or made by a bot's `crew.add`); the deployment rule `MaxBotsPerSpace` caps it, and a space's own value can only lower that ([16-deployment-policies.md](16-deployment-policies.md)). The count is taken under a per-space advisory lock that every change to the tree's shape takes first, so two additions count one after the other. The child's `depth` is the parent's plus one, and its `bot_ancestors` rows are its own at distance 0 and the parent's rows each one step further. Of the tools every new bot starts with, the child gets each only as far as the parent's `effective_grants` give it: lowered to the parent's effect, and left out when the parent has none. The `bot.created` audit entry names the parent.
- A bot granted the crew tools makes, changes, pauses, and removes the bots beneath it through the same code, acting for its run's person ([04-tenancy-and-permissions.md](04-tenancy-and-permissions.md#authority-in-the-tree)). A bot it makes has `created_by_bot_id` set to it and `created_by_user_id` to that person; a bot a person made has `created_by_bot_id` null. `BotSummary.MadeByBotId` and `BotDetail.CreatedByBotId` carry it. Its grants carry `granted_by_bot_id` the same way.
- Removing a bot that has bots beneath it needs a choice for them, and is refused in words without one ([04-tenancy-and-permissions.md](04-tenancy-and-permissions.md#pausing-and-removing)). With `remove`, every bot of the branch is marked `removed`. With `keep`, each bot directly beneath moves up to the removed bot's parent, or to the top: `parent_bot_id` changes on it alone, and for it and every bot beneath it the closure row to the removed bot is deleted, every row to a bot above the removed one comes one step nearer, and `depth` drops by one. Removed bots inside a moved branch move with it, so the closure table stays whole.
- `bot_ancestors` is a closure table that includes each bot's row to itself at distance 0. "Is X beneath Y" is one primary key lookup; "everything beneath Y" is one indexed scan. It is plain relational data, needs no extension, and is rewritten only when the tree changes, which is rare.
- `bot_rules` holds a bot's rules: limits a person writes and the server enforces in code, described in [04-tenancy-and-permissions.md](04-tenancy-and-permissions.md). `checkpoint` is `before_tool`, `after_tool`, `before_reply`, or `message_arrives`; `effect` is `redact`, `ask`, `block`, or `stop`; `conditions` is a list of at most ten typed conditions, validated at save. A bot has at most fifty. A bot follows its own rules and those of every bot above it, read through `bot_ancestors`; no row and no column lets a child switch an ancestor's rule off.
- `tool_grants.effect` is `allow`, `ask`, or `deny`. No row means the bot cannot see the tool. `review_state` is `current` or `needs_review`; see tool definition pinning in [06-mcp.md](06-mcp.md).
- Model settings, memory settings, and sandbox settings are `jsonb` mapped to C# records owned by `Drover.Domain`. They are provider-neutral: `temperature`, `max_output_tokens`, `reasoning_effort`, not a vendor's option names.
- `model_settings` holds `temperature`, `max_output_tokens`, `reasoning_effort`, `web_search` (`off`, `on`, `automatic`), and `structured_output`, which asks the model for a JSON object. The server refuses a setting the model's capability record says it lacks; a model the catalog does not know is taken on trust.
- `memory_settings` holds `enabled`, `compaction` (`none`, `sliding_window`, `summarization`, `tool_results`, `truncation`), `compact_at_tokens`, `keep_recent_messages`, `max_note_characters`, and `max_notes_characters`. They are stored and edited now. `enabled` turns the bot's notes about its person on (see `memories` below); off, its memory tools are not offered and nothing is recalled. `max_note_characters` and `max_notes_characters` narrow the server's limits on notes; the editor does not show them yet and saves them back unchanged. Of the rest the runtime applies only `compaction` = `summarization`, and only on a main thread that has a summary: the history given to the model is then the thread's summary, as a labeled first message, followed by the messages after `summary_through_position` (see `is_main` below and [03-run-lifecycle.md](03-run-lifecycle.md#conversation-summaries)). `compact_at_tokens`, `keep_recent_messages`, and every other `compaction` value change nothing yet: the whole conversation is given.
- `avatar` holds an optional `emoji` and `file_id`. With neither, the interface draws the bot's character from its name and id.
- Every column of `bots` that a person may set has a path through the API, and a test walks the entity to hold that. `id`, `parent_bot_id`, `depth`, and the two `created_by` columns are set by the server; `status` changes through pause, resume, and remove, and remove is soft: the row and its history stay.
- A schedule's `next_run_at` is computed when the schedule is saved, in UTC, from its cron expression and time zone, and again each time it comes due, counted from that moment. A schedule that is off has none. While the scheduler holds a claim on it, it is the end of that claim ([03-run-lifecycle.md](03-run-lifecycle.md#schedules)). `last_run_id`, `last_run_at`, and `last_outcome` say what happened the last time it was due; `last_run_id` has no foreign key, so a run can be removed without touching the schedule that started it; a status read for a run that is gone is simply not shown.
- `messages.schedule_id` names the schedule that sent a message for its author, who did not type it. It has no foreign key, so the message still reads as sent by a schedule after the schedule is removed.
- Setting a tool to off in the editor deletes the bot's `tool_grants` row. Setting it is refused when it would exceed what the parent's `effective_grants` gives. No write in the bot editor clears a review: changing a grant's effect leaves its `review_state` alone, a first grant on a tool whose changed definition nobody has accepted is created `needs_review`, and a duplicated bot gets the source's own grants with their review state, lowered to what the source's parent holds. A grant that waits is made current only by accepting the tool's changed definition, which the editor offers beside the tool together with what was last reviewed.
- Bot, grant, and schedule changes each write one `audit_log` row in the same transaction: `actor_kind` `user`, the actor's id (or `actor_kind` `bot` and the bot's id when a bot made the change with a crew tool, with the person it acted for in `data.for_user_id`), an `action` such as `bot.updated` or `grant.changed`, `target_kind` `bot`, and `data.changes` holding only the values that changed, each with `before` and `after`. A grant is recorded as its stored `effect` and `review_state`, so a `deny` and no row are told apart, and `bot.created` and `bot.duplicated` list the tools the new bot was given. A person's action on a bot's sandbox writes one row after it is done, in a short transaction of its own because the provider is called between: `sandbox.paused`, `sandbox.resumed`, `sandbox.rebuilt`, `sandbox.turned_off`, `sandbox.command`, or `sandbox.input` with `data.input` naming the kind (`click`, `type`, `key`, `scroll`), `target_kind` `bot`. Never the text typed, the command, or a picture ([07-sandbox.md](07-sandbox.md#people-and-the-sandbox)).
- Removing a bot deletes the sandbox shares it gave and was given.
- Model and memory numbers are bounded for every model, known to the catalog or not, and `reasoning_effort` is one short word: each change is copied into the append-only audit log.

### Skills, reserved shape

Not created in Phase 0. The model leaves room for them without redesign:

| Table | Key columns |
| --- | --- |
| `skills` | `id`, `name`, `description`, `instructions`, `source`, `trust`, `content_file_id null`, `content_hash` |
| `bot_skills` | `bot_id`, `skill_id`, `enabled`, `position` |

A bot's instructions are assembled by the engine from an ordered list of instruction sources: the bot's own text first, then each enabled skill's description, with the skill body loaded on demand. Phase 0 has one source. A skill's scripts run only in the bot's sandbox, and a skill never carries grants: it can use only the tools the bot already holds. `trust` is always `untrusted` for imported content, which means its text is presented to the model as reference material, never as system instructions.

## Tools and connections

| Table | Class | Key columns |
| --- | --- | --- |
| `model_connections` | Space-owned | `id`, `name`, `kind`, `base_url`, `auth_kind`, `credential_scope`, `secret_id null`, `default_model`, `status`, `balance jsonb`, `last_checked_at` |
| `model_catalog` | Space-owned | `model_connection_id`, `model`, `display_name`, `capabilities jsonb`, `pricing jsonb`, `privacy_mode`, `traits`, `state`, `last_seen_at` |
| `tool_connections` | Space-owned | `id`, `name`, `slug`, `url`, `transport`, `auth_kind`, `credential_scope`, `oauth jsonb`, `trust`, `status`, `last_listed_at`, `last_error` |
| `tool_connection_credentials` | Space-owned with an audience | `id`, `tool_connection_id`, `audience_user_id`, `secret_id`, `expires_at`, `status` |
| `tools` | Space-owned | `id`, `source_kind`, `tool_connection_id null`, `name`, `title`, `description`, `input_schema jsonb`, `annotations jsonb`, `definition_hash`, `sensitivity`, `state`, `first_seen_at`, `last_seen_at` |
| `oauth_flows` | Space-owned with an audience | `state_hash`, `audience_user_id`, `tool_connection_id`, `expires_at` |

Notes:

- `model_connections.kind` is `openai_compatible`, `venice`, `anthropic`, or a sign-in kind. `model_catalog` holds one capability record per model, in Drover's own shape ([15-model-providers.md](15-model-providers.md)). Sign-in connections keep per-user credentials in `secrets` with that user as the audience.
- `tool_connections` also stores `protocol_mode` (automatic, stateless only, session-based only) and what was negotiated.
- `tools.source_kind` is `builtin` or `mcp`. Built-in tools are rows in each space's catalog, so a grant always references a `tools` row and the grant logic has one shape. The rows are added, and refreshed when a definition changes, whenever a bot is created in the space. The catalog name of a built-in uses dots (`time.now`); the model sees it with underscores (`time_now`), because providers do not accept a dot in a function name.
- `tools.state` is `available` or `missing`. A tool that disappears from a server keeps its row and its grants, marked missing.
- `tool_connections.auth_kind` is `none`, `header`, or `oauth`. `credential_scope` is `space` or `per_user`.
- A `tool_connection_credentials` row whose audience is everyone is a credential shared by the whole space. A row whose audience is one user is readable only inside a transaction running for that user. That is how a bot acting for one person cannot use another person's sign-in: the database will not return the row.

## Conversations and runs

| Table | Class | Key columns |
| --- | --- | --- |
| `threads` | Space-owned with an audience | `id`, `bot_id`, `owner_user_id`, `audience_user_id`, `title`, `origin`, `last_activity_at`, `archived_at null`, `is_main`, `summary null`, `summary_through_position null`, `summary_updated_at null` |
| `messages` | Space-owned with an audience, inherited from the thread | `id`, `thread_id`, `audience_user_id`, `position null`, `steers`, `withheld`, `role`, `author_user_id null`, `author_bot_id null`, `run_id null`, `schedule_id null`, `parts jsonb`, `created_at` |
| `thread_reads` | Space-owned with an audience: the person whose marker it is | `thread_id` (no foreign key), `audience_user_id`, `seen_through_position`, `seen_at`. Primary key `(space_id, thread_id, audience_user_id)` |
| `runs` | Space-owned | `id`, `thread_id`, `bot_id`, `principal_user_id`, `trigger`, `trigger_message_id null`, `parent_run_id null`, `root_run_id`, `parent_tool_call_id null`, `depth`, `status`, `status_reason`, `error jsonb`, `tainted`, `attempt`, `lease_owner null`, `lease_expires_at null`, `cancel_requested_at null`, `last_event_seq`, `usage jsonb`, `subtree_usage jsonb`, `started_at`, `finished_at`, `waiting_since null` (when the run last began to wait for a person) |
| `run_events` | Space-owned with an audience, inherited from the thread | `root_run_id`, `seq`, `run_id`, `thread_id`, `audience_user_id`, `type`, `data jsonb`, `created_at`. Primary key `(space_id, root_run_id, seq, created_at)`, because PostgreSQL requires the partition column in every unique key |
| `tool_calls` | Space-owned with an audience, inherited from the thread | `id`, `run_id`, `thread_id`, `audience_user_id`, `tool_id`, `tool_name`, `arguments jsonb`, `status`, `result jsonb`, `result_file_id null`, `is_error`, `decided_by_user_id null`, `decided_at null`, `child_run_id null`, `sandbox_id null`, `started_at`, `finished_at` |
| `usage_records` | Space-owned | `id`, `run_id`, `root_run_id`, `bot_id`, `model_connection_id`, `model`, `input_tokens`, `output_tokens`, `cached_tokens`, `cost` (null when the catalog does not know the price), `currency`, `created_at` |

Notes:

- `agent_sessions` (space-owned with an audience, inherited from the thread): `thread_id`, `bot_id`, `state json`, `framework_version`, `updated_at`. The agent framework's serialized session, including any pending approval. `state` is `json`, not `jsonb`: the framework's polymorphic JSON needs its `"$type"` property kept first, and `jsonb` reorders object keys, which made a stored session fail to deserialize (found by the step 7 spike). The same holds for workflow checkpoints in Phase 1. Opaque working state: if a framework update cannot read it, it is discarded and the session is rebuilt from `messages`.
- `workflow_checkpoints` (same class, Phase 1): `run_id`, `checkpoint_id`, `parent_checkpoint_id null`, `state json`, `framework_version`, `created_at`. Team runs resume from the latest one.
- `messages.parts` is an ordered array of Drover's own part records: `text`, `reasoning`, `image`, `file`, `tool_call`, `tool_result`. An `image` or `file` part names its `files` row and carries the facts the conversation shows (name, size, a picture's width and height, a text file's first lines), copied from the row when the message is sent, and the caption a bot wrote for a file it shared. This is Drover's schema, defined in `Drover.Domain`. No vendor message type is ever serialized into it. A `tool_call` and its `tool_result` carry two ids: `tool_call_id`, the `tool_calls` row, and `call_id`, the id the model gave the call, which pairs call and result when the history is sent back to a model. The row id is derived from the run and the model's call id, so every part of a run finds the same row without a lookup column. Approval requests and responses are not message parts: they are working state, kept in the agent session and in `tool_calls`.
- `messages.position` orders a thread. It is null while a message is pending: sent while the bot was working, stored, and not yet part of the conversation. A run gives it its position when it takes it. `steers` says a pending message joins at the working run's next step instead of after the run; it is false once the message has a position. `run_id` on a person's message names the run that took it. See [03-run-lifecycle.md](03-run-lifecycle.md#a-message-sent-while-the-bot-is-working).
- `runs.principal_user_id` is the human the run acts for. A child run inherits it unchanged from its parent. Scheduled runs use the schedule's owner.
- `runs.root_run_id` equals `id` for a root run. `last_event_seq` is used only on the root row.
- `runs.status` values and transitions are in [03-run-lifecycle.md](03-run-lifecycle.md).
- `tool_calls` is a first-class table, not only events, because the activity view, the approval inbox, and restart recovery all query it by status.
- `tool_calls.arguments` and `result` are stored after redaction ([08-auth-and-secrets.md](08-auth-and-secrets.md)). Large results go to a file and the row keeps a preview.
- A thread is private to its owner by default. Sharing it with the space sets its audience to everyone, and the cascade carries that to its messages, events, and tool calls. A check constraint allows only two audiences for a thread, its owner or everyone, and the app role has no privilege to update `owner_user_id`, so one member cannot take over another's thread.
- A delegated child run's thread inherits the audience of the root thread.
- `is_main` marks a person's one main thread with a bot, the conversation a person lands in when they pick the bot; every other thread with it is a side chat. A unique index over `(space_id, bot_id, owner_user_id) where is_main` allows at most one per person per bot. `PUT .../bots/{botId}/main-thread` returns the caller's main thread and makes it when there is none: private to them, origin `chat`, no title. It makes one only while the bot is active, the same rule as making any thread. Two requests that race insert with `ON CONFLICT DO NOTHING` on that index, so the one that loses stores nothing, keeps a usable transaction, and reads the winner's row. A side chat with no title is named after its first message; a main thread never takes a title that way. The migration that added the column made each person's open (not archived) `chat` thread with the latest `last_activity_at` their main one with that bot. Because the policies are forced on the table's owner too and a migration has no tenant, that one statement runs with the policies switched off for the owner and forced again inside the migration's transaction.
- `summary` is the server's running summary of a main thread, `summary_through_position` the position of the last message it covers (positions start at one and have no gaps, so it is also how many messages it covers), and `summary_updated_at` when it was last rewritten. They are columns of the thread's own row, not a table, so the summary has exactly the thread's audience with nothing more to keep in step: another member, an admin included, cannot read a private thread's summary, and sharing the thread shares it. A check constraint (`ck_threads_summary`) holds that text and reach are set together and only on a main thread. The application role may update the three columns, and only the server writes them, in one statement that also requires the reach it read to be unchanged ([03-run-lifecycle.md](03-run-lifecycle.md#conversation-summaries)). `GET .../threads/{threadId}/summary` serves it as `ConversationSummary` (text, messages covered, updated at), with the same 404 as reading the thread; a side chat, or a main thread with no summary yet, answers with no text.
- A foreign key to an audience table must carry `audience_user_id` (the isolation suite checks this), so a table with no audience column, or with an audience that differs from its parent's, cannot have one. That is why these are plain `uuid` columns with no foreign key: `thread_reads.thread_id`, `runs.thread_id`, `runs.trigger_message_id`, `runs.parent_tool_call_id` (runs are metadata with no audience), `tool_calls.result_file_id`, `model_connections.secret_id`, `sandboxes.access_secret_id`. The application sets them from rows it has just read inside the same space.
- Sharing a thread is one `UPDATE threads SET audience_user_id = ...`. The audience is part of an alternate key, so EF Core refuses to change it through a tracked entity; the service uses `ExecuteUpdate` or SQL.
- Settings and value records (`model_settings`, `memory_settings`, `sandbox_settings`, `build_limits`, `avatar`, `usage`, `error`, `capabilities`, `pricing`, `balance`, `oauth`, message `parts`) are records in `Drover.Domain`, stored as snake_case JSON. Message parts are defined in `Drover.Domain`, not `Drover.Contracts`. Open-shaped payloads (`input_schema`, `annotations`, tool `arguments` and `result`, event `data`, session `state`) are plain JSON.
- `thread_reads` is how far each person has seen each thread: the newest message position they had in front of them and when. It is on the server so every screen of theirs agrees. Its audience is the person whose marker it is, so the audience policy shows it to them alone and refuses a row addressed to anyone else: on a thread every member shares, no member reads or writes another's marker. The server reads only markers addressed to the caller, so a row addressed to everyone, which the policy would allow, counts for nobody. `thread_id` is a plain `uuid` with no foreign key, like `runs.thread_id`: a key to the thread would have to carry the thread's audience, and a shared thread's audience is everyone. `PUT .../threads/{threadId}/seen` moves the marker to the thread's newest message, never backwards, and answers 404 to anyone who cannot read the thread. The migration that added the table marked every existing thread seen by every member who could see it (its owner, or every member of the space for a shared thread), with the policies switched off for the owner for that one statement, as the main-thread migration did.
- What a thread has for a person is read from stored rows and that person's own only, because runs have no audience: their newest root run in the thread (waiting with a call anywhere in its delegation tree still unanswered, or failed after their `seen_at`), and replies from runs of theirs past their `seen_through_position`. Every `ThreadSummary` carries it as `Attention`; see [03-run-lifecycle.md](03-run-lifecycle.md#streaming-and-resume).
- `messages.withheld` is true for a person's message that one of the bot's rules did not let through. The message stays in the thread for the people who can read it, and no model is ever given it: the history handed to a model leaves it out, in the run that refused it and in every later one.
- Values of the status and kind columns this document does not list elsewhere: `model_connections.auth_kind` is `none`, `api_key`, or `sign_in`; connection `status` is `pending`, `ready`, `failed`, or `disabled`; `tool_connections.transport` is `streamable_http` or `sse`; `trust` is `trusted` or `untrusted`; `protocol_mode` is `automatic`, `stateless_only`, or `session_only`; credential `status` is `active`, `needs_reconnect`, or `expired`; `tools.sensitivity` is `read`, `write`, or `critical`; `bot_schedules.thread_mode` is `new_thread` or `same_thread`; `bot_schedules.last_outcome` is `started`, `waiting_for_reply`, `bot_paused`, `bot_removed`, or `owner_left`; `threads.origin` is `chat`, `schedule`, or `delegation`; `runs.trigger` is `message`, `schedule`, or `delegation`; `tool_calls.status` is `pending_approval`, `approved`, `denied`, `running`, `completed`, `failed`, or `interrupted`; `messages.role` is `system`, `user`, `assistant`, or `tool`. Each is a text column with a check constraint that lists its values.

`sandboxes.state` is `creating`, `running`, `paused`, `retiring`, or `destroyed`.

Notes on `files`:

- A file a person attaches belongs to the conversation it was attached in. Its key to the thread is `(space_id, thread_id, audience_user_id)` with `ON UPDATE CASCADE`, so a file is seen by exactly the people who see its conversation, and sharing the thread shares its files. The one copy kept outside the row is in a bot's sandbox, which the space's admins and the bot's runs for other people can reach, so the server copies a file there only when the conversation is shared with the whole space, or the space is personal and has exactly one member, checked against the members at copy time ([07-sandbox.md](07-sandbox.md)). `thread_id` is null only for a file that belongs to no conversation; none is made yet.
- A file a bot shares from its sandbox (`sandbox.share_file`, see [07-sandbox.md](07-sandbox.md#sharing-a-file-into-the-conversation)) has `created_by_bot_id` set and no `created_by_user_id`. It takes the audience of the conversation whose run shared it, and `message_id` is the bot's reply that asked for it, set in the same transaction that adds the part. Its id is the tool call's.
- `message_id` is null while the file waits to be sent, and names the message that carries it after. It is a plain column: the thread's key already carries the audience, and a second cascading key through `messages` would give one row two cascades. The server sets it from a message it has just stored, in the same transaction. A sent file is kept as long as its message; a file not yet sent can be removed by the person who attached it.
- `content_type` is chosen by the server from the bytes (`FileInspector`), never taken from the browser: a PNG, JPEG, GIF, or WebP whose header gives its size is a picture (`width` and `height` set), UTF-8 with no NUL byte is text (`preview` holds its first lines), and anything else is another kind. The content type alone says which of the three a file is.
- `storage_key` is `{space_id}/{file_id}`, each as 32 hexadecimal digits, and nothing else: no name a person typed is ever part of it. Every `IFileStore` call names the space it acts for and refuses a key that is not that space's (`FileStorageKeys`), and a file is only ever opened after its row has been read in a tenant scope, so the row decides who may read it, never the key.
- `spaces.stored_file_bytes` counts the bytes of every file in the space, so `MaxSpaceFileMegabytes` holds across members without anyone reading another member's rows. An upload raises it in the same statement that checks the limit (`UPDATE ... WHERE stored_file_bytes + size <= limit`), so two uploads at once cannot both pass; removing a file not yet sent lowers it. Before that, an upload's bytes are cut off at the space's room as well as at `MaxFileBytes`, so a body that declares no length never fills the disk past what the space may hold.
- The bytes are on the server's disk (`Drover.Adapters.LocalFiles`), under `Files:Path` (`/var/lib/drover/files` in the image). Nothing scans them for viruses.

`memories` holds the short notes a bot keeps about the person it works for: one fact or preference each, in the bot's own words, rewritten when it changes instead of added to. A note belongs to one bot (`bot_id`) and, through `audience_user_id`, to the one person it is about; row-level security keeps it from every other member and every other space. Who wrote it is the bot or a person, never both (`ck_memories_writer`). A note the bot wrote names the conversation and the message it came from, both or neither (`ck_memories_source`). They are plain columns on purpose, like `tool_calls.result_file_id`: a key to `messages` would have to carry the audience, and an audience key moves with its parent, so sharing a conversation would share every note taken from it and deleting a conversation would be blocked by its notes. A note's audience is its person's alone and never moves, and a conversation or an account can be deleted whatever notes came from it. `MemoryService` names only the reply that made the call, in a conversation private to the run's person, and refuses any other. `tainted` is set when the run that wrote the note had read text from an untrusted source, and once set it stays (below). `text` is one line, at most 1,000 characters in the column, and never blank; the limits a bot actually obeys are smaller (below). `updated_at` is when the text was last written.

How notes are kept and read:

- A bot keeps and reads notes only while its `memory_settings.enabled` is on, and only through the four built-in memory tools, `memory.save`, `memory.change`, `memory.forget`, and `memory.list`, granted like any tool and granted to no new bot by default. They act on the calling bot's own notes about the run's person and nothing else, inside one short transaction as that person (`MemoryService`). `memory.save` and `memory.change` keep the text after the run's redactor has taken out anything it knows to be secret, on one line: line breaks and other control characters become spaces (`NoteText.Flatten`), so a note cannot lay out text that passes for another note or for what a person said.
- A note written by a tainted run ([06-mcp.md](06-mcp.md)) is `tainted`, and a change keeps it so. A run that is given a tainted note is tainted before its agent is built, so attacker text that reached a note in one run cannot drive an `allow` tool in a later run without the tainted-run rule applying.
- Notes are kept and read only in a conversation private to the run's person. In a shared conversation the memory tools are not offered, nothing is recalled, and a call is refused: a private note read into a conversation others see would show it to them. Notes shared by everyone in a shared space are the reason `audience_user_id` may one day be `sys.everyone()`; nothing writes such a note yet.
- One note is at most `memory_settings.max_note_characters`, and a bot's notes about one person together at most `memory_settings.max_notes_characters`. Each left empty takes the server's limit, and neither may exceed it: `MaxMemoryNoteCharacters` (1,000, hosted 500) and `MaxMemoryCharactersPerPerson` (20,000, hosted 8,000) ([16-deployment-policies.md](16-deployment-policies.md)). A save or change past either is refused with a sentence that says how much is used and tells the bot to merge notes with `memory.change` or remove them with `memory.forget`. Nothing is dropped silently. The count is taken under an advisory lock on the bot and the person, so two saves cannot together pass the limit.
- At the start of every run that is offered a memory tool, the bot's notes about the run's principal are read in the run's load transaction and given to the model as reference material, never as instructions, each as one quoted line after its id ([14-agent-framework.md](14-agent-framework.md)). When they do not all fit, the most recently written are kept. The principal is the person the run acts for whatever started it, so a run started by a schedule or by delegation recalls the notes of that person.
- A person reads, adds, rewrites, and removes their own notes for a bot through `/api/spaces/{space}/bots/{bot}/memory` (`MemoryService.ListForPerson`, `AddByPerson`, `ChangeByPerson`, `RemoveByPerson`, `RestoreByPerson`), under the same row-level security: another member's or an admin's request finds none of them. The list comes newest change first, with each bot-written note's message when its conversation is still the person's to open, and says the notes are nearly full from nine tenths of `max_notes_characters`. It is served with memory off too, so a person can always see and remove what is kept about them; adding and rewriting are refused while memory is off, with the same limits and advisory lock a bot's save takes. A note a person adds is theirs (`written_by_user_id`) and never tainted. A clean note a person rewrites becomes theirs and loses its source columns. A person's edit never clears `tainted`: no edit proves that nothing the tainted run read is left, so a tainted note keeps its bot writer and the message it came from whatever the person writes, and a person who wants a clean note removes it and adds their own. Removing a note returns an `Undo` receipt and the time it runs out (`UndoUntil`, ten minutes on): the removed row, its writer, source, and `tainted` included, with that time sealed in, protected with ASP.NET Core data protection under a purpose naming the person and the space. Restoring unseals it, refuses it once the server's clock has passed that time or for another bot, and puts the same row back within the bot's current limits, memory on or off, so a client can put a note back but cannot change who wrote it or clear its taint. A conversation card's Forget removes the note only while it still says what the card shows (`POST …/notes/{id}/forget`), and is answered 409 once it has changed.
- Finding notes by meaning, with a `vector` column and embeddings, is a later issue.

`run_events` grows fastest. It is range-partitioned by month on `created_at` from the first migration, so old partitions can be detached or dropped without a table rewrite.

The first migration creates fourteen monthly partitions, November 2026 to December 2027, and a default partition that takes any row outside them, so an insert never fails for want of a partition. Creating the next months ahead of time is a maintenance job that does not exist yet. The application role holds privileges on `run_events` only, never on a partition, so every read and write goes through the table's policies. Each partition also has row-level security enabled and forced with no policy, which denies everything if a privilege is ever granted by mistake.

Because the key carries `created_at`, the database does not enforce that `(root_run_id, seq)` is unique. The lock on the root run row does: sequence numbers are only ever given out by the `UPDATE ... RETURNING` in [03-run-lifecycle.md](03-run-lifecycle.md).
