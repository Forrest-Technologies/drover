# 15. Model providers

Facts in this section were read from each provider's own documentation and live API on 2026-11-11.

## Shape

A **model connection** is data: a kind, an address, a way to authenticate, and what was learned about its models. `IModelClientProvider` turns a `ModelEndpoint` into a Drover-owned `IModelChatClient` and lists/tests the connection. `ModelConnection` remains the space-owned persistence entity, with no credentials in either shape. Embeddings remain future work. One adapter project per vendor package: a vendor package is referenced by exactly one `Drover.Adapters.*` project (AGENTS.md section 4), so every kind built on the OpenAI package (`openai_compatible`, `openai`, and the sign-in kinds that reuse its clients) lives in `Drover.Adapters.OpenAICompatible`, and a kind with its own package gets its own project.

The providers are wired into the server by `AddDroverModels` (`Drover.Server`), one `AddModelProvider<TProvider>` call each, the compatible transport before Venice, then OpenAI, then Anthropic, and returned clients are bridged with `ModelChatClientBridge`. Every provider call uses a named HTTP client from `IHttpClientFactory`, and `AddModelProvider` puts `SpaceOutboundHandler` on each client name it is given, so the checked outbound handler of the deployment policy applies to model connections and an adapter cannot be registered without it. An adapter builds its own requests and knows nothing of policy, so the caller wraps the adapter call in `OutboundAttempt.Begin(effectivePolicy)` and `SpaceOutboundHandler` puts the space's `AllowPrivateAddresses` value on each request made inside it; a request made outside any attempt says nothing and is treated as forbidden. When the handler refuses an address, the adapter maps the refusal to a rejected failure that carries its own message, so the connection test says why instead of "could not be reached"; a refusal is one attempt, never retried and never counted toward the circuit breaker. No tenant transaction is held across these provider calls.

## Provider kinds

A provider is a `Drover.Adapters.*` project compiled into the server and added by one registration call ([ADR 0024](../adr/0024-providers-are-compiled-in-adapters.md)); Drover never loads provider assemblies at run time. `AddModelProvider<TProvider>(addAdapter, httpClients)` runs the adapter's own registration, checks that it registered `TProvider`, and adds `SpaceOutboundHandler` to every named HTTP client in `httpClients`. A new kind is one more call in `AddDroverModels` and a conformance test class.

**The descriptor.** `IModelClientProvider.Descriptor` is a `ModelProviderDescriptor` (`Drover.Domain.Models`): `Kind`, `DisplayName`, `KeyRule` (`Required`, `Optional`, `None`), `AddressRule` (`Fixed`, `Required`), `AddressHint`, `KeyHint`, `SignIn` (true for a sign-in kind, which a client draws with its sign-in screen and never with a key form: the connect list leaves such kinds out of the kinds it takes a key for), and `ReportsCapabilities` (true when the provider's model list carries capabilities and prices, as Venice's does; a compatible endpoint's does not). It holds words and rules only: never a key, a header, an address of the provider, or a balance. `FixedAddress` stays a separate member of the provider and never leaves the server. The conformance suite checks that a provider's descriptor names its own kind and matches its behavior: the address rule is `Fixed` exactly when `FixedAddress` is set, and a provider whose key is `Required` refuses a missing key with the invalid-key setup message while one whose key is optional or none answers without one (`A_provider_describes_itself_with_a_kind_a_name_and_rules_that_match_its_behavior`).

| Kind | Name | Key | Address | Reports capabilities |
| --- | --- | --- | --- | --- |
| `openai_compatible` | Compatible endpoint | Optional | Required | No |
| `venice` | Venice | Required | Fixed | Yes |
| `openai` | OpenAI | Required | Fixed | No |
| `anthropic` | Anthropic | Required | Fixed | No (its list says what each model can do, but carries no prices) |
| `gemini` | Google Gemini | Required | Fixed | Yes |
| `openai_signin` | ChatGPT plan (each person signs in) | Required (the person's token) | Fixed | No |
| `copilot_signin` | GitHub Copilot (each person signs in) | Required (the person's GitHub token) | Fixed | Yes |

**The catalog.** `ModelProviderCatalog` (`Drover.Engine`, a singleton) holds the registered providers in registration order and answers which are offered. It is built when the server starts (`ModelProviderStartupCheck`): two providers with one kind, or a provider whose descriptor names another kind, stop the server with a sentence that names the kind. Every place that picks a provider for a connection asks it, so the deployment policy applies to a test, a refresh, a run, a screen reader, a summary, an image, and speech alike.

**The route.** `GET /api/model-provider-kinds` answers a signed-in person with the kinds this server offers, in registration order (Venice, OpenAI, Anthropic, Gemini, the ChatGPT plan, the Claude plan, OpenRouter, GitHub Copilot, then the compatible kind, so a form starts on a provider that needs only a key and ends on "Another compatible server"; `AddDroverModels` is where the order is set and `ModelProviderKindTests` pins it), as `ModelProviderKindResponse` (`Kind`, `DisplayName`, `KeyRule` and `AddressRule` as the words in `ModelKeyRules` and `ModelAddressRules`, the two hints, `ReportsCapabilities`, and for a sign-in kind `SignIn`, its `SignInName` for the button and the provider's public `UsagePage`). It is the same for everyone and is not in a space. A signed-out caller gets 401. `DroverApi.ListModelProviderKinds` is the client's call.

**Which kinds are offered.** The deployment policy rules `ModelProviders` and `AllowedModelProviderKinds` ([16-deployment-policies.md](16-deployment-policies.md)): under `All` every registered kind is offered; under `OperatorList` (the hosted preset, or an operator's choice) only the kinds in the list. A kind that is not registered or not offered cannot be given to a new connection (`POST /api/spaces/{spaceId}/model-connections` answers 400 with "The kind {kind} is not available on this server." or "The operator of this server switched {kind} off."). A connection that already exists keeps being listed, and its next call fails with "The operator of this server switched {kind} off." without reaching the provider. The rule only narrows: no space setting turns a kind back on.

## Connections in a space

A connection is created and managed under `/api/spaces/{spaceId}/model-connections`. Antiforgery applies to every state-changing request.

| Route | Who | What |
| --- | --- | --- |
| `GET /` | member | The space's connections. A connection says `hasKey`; the key is never returned. |
| `POST /` | admin | Create. `kind` is a registered provider kind that the deployment offers ([Provider kinds](#provider-kinds)); any other is refused with a sentence that names it. A fixed-address kind (Venice) takes no address; a compatible endpoint needs an `http`/`https` address with no credentials, query, or fragment. The key is optional and goes to `ISecretVault` as a `model_key`. |
| `PUT /{id}/key` | admin | Store a new key as a new secret and delete the old one, then return the connection to `pending`. |
| `POST /{id}/test` | admin | Ask the provider whether the connection works. Records `ready` or `failed`, the time, and any balances. A rate-limit answer leaves the status alone. A passing test makes a second provider call to list models and refreshes the stored catalog as `POST /{id}/models/refresh` does. A failed listing leaves both the catalog and the test result alone. |
| `GET /{id}/models` | member | The stored catalog (`model_catalog`), in Drover's own shape, with the effective capabilities and prices and `operatorSet`. |
| `POST /{id}/models/refresh` | admin | Discover the provider's models and upsert the catalog. A model that is no longer listed keeps its row, marked `missing`. An empty list marks nothing missing. If the provider cannot answer, the stored catalog is returned with the reason. |
| `POST /sign-in` | member | Start the caller's own sign-in to a sign-in kind (below). |
| `POST /sign-in/{attemptId}/finish` | the member who started it | Finish it with what the device received. |
| `GET /sign-in/{attemptId}` | the member who started it | Where it stands. |
| `DELETE /{id}/sign-in` | member | Sign the caller out of their own sign-in. |

`POST /` and `PUT /{id}/key` refuse a sign-in kind: each person connects it by signing in. A connection's summary carries `signIn`: null for a key connection, otherwise the caller's own sign-in only (`none`, `active`, `needs_sign_in`, and the account label the provider reports). It never says who else has signed in. A test of a sign-in connection uses the admin's own sign-in, and one person's missing or ended sign-in is not recorded on the connection.

Creating a connection to a literal private address is refused when the space or the deployment forbids private addresses; a host name is checked each time a connection is made, because what it resolves to can change.

Model discovery is bounded. Adapters read a model list with headers first and stop at `MaxModelListBytes`; `ModelConnectionService` refuses a list with more than `MaxModelsPerConnection` models. Both are deployment policy rules ([16-deployment-policies.md](16-deployment-policies.md)) and a refused list leaves the stored catalog alone. An answer the adapter cannot read is a rejected failure, not a server error. Two refreshes that add the same model both succeed: the save that loses the primary-key race reads the catalog again and updates the row.

Create, replace-key, and the two reads run under the tenant scope filter. Test and refresh wait on the provider, so they sit outside the filter and `ModelConnectionService` opens its own scopes: one to read the connection, reveal the key, and work out the space's rule; then the provider call with no scope open; then a new scope to write. A passing test records its result before making a second provider call to list models, also with no scope open, then writes the catalog in another scope using the same upsert as refresh. A failed listing leaves the stored catalog and the recorded test result alone. If the key or address changed while either provider call was answering, that call's answer is not written. Balances are stored on the connection as a list (Venice reports both `usd` and `diem`), each a snapshot from before the request; `RecordBalances` is the call a run uses after a reply.

The boundary preserves text, images, reasoning (including opaque protected reasoning), function declarations/calls/results, structured output, streaming, citations, and usage including cached/reasoning counts. Function results retain their JSON value shape; exception objects are replaced by a safe failure indication. Tool calls with an SDK argument-parse failure are rejected with a fixed message before the agent framework can execute them; a valid no-argument call remains valid. Unknown content/tool kinds, non-object tool arguments, background/continuation options and provider-specific option objects fail explicitly rather than disappearing. The Venice adapter applies a bot’s JSON-only reply setting only when the request cannot call tools. An explicit response format still takes precedence. Agent history, approvals, tool invocation and orchestration continue to use Microsoft Agent Framework inside `Drover.Agents`.

| --- | --- | --- | --- |
| `openai_compatible` | API key, or none for local models | `Drover.Adapters.OpenAICompatible` | 0 |
| `venice` | API key | `Drover.Adapters.Venice` | 0 |
| `openai` | API key, on the Responses API ([OpenAI](#openai-on-the-responses-api)) | `Drover.Adapters.OpenAICompatible` | 1 |

| `copilot_signin` | The user's own GitHub Copilot plan, through a GitHub OAuth app the operator registers ([GitHub Copilot](#github-copilot-for-self-hosted-servers)) | `Drover.Adapters.OpenAICompatible` | 1 |

Every adapter must pass the model provider conformance suite: list models, plain reply, streaming, tool call round trip, structured output where claimed, reasoning text where claimed, protected reasoning sent back unchanged in a tool loop where claimed, cached input tokens reported where claimed, a rate-limit response mapped to "retry later", an invalid key mapped to a clear setup message. The suite reads the wire through `IChatWire` (`tests/Drover.Adapters.Conformance/ChatWire.cs`), which each adapter's test class gives on its `ProviderUnderTest`: which requests are model calls, the tool names offered, the text sent back for a tool call, the structured output asked for, and the protected reasoning sent back. `ChatCompletionsWire` is the default and serves the compatible and Venice adapters; `ResponsesWire` serves OpenAI, `AnthropicWire` serves Anthropic and `GeminiWire` serves Gemini. A wire also gives the PDFs a call sent as documents (`SentPdfs`, empty where it has none) and says whether it names a schema (`NamesSchemas`: Anthropic's and Gemini's send the schema alone). `ConformanceClaims` says which optional features an adapter's test model has: `StructuredOutput`, `ReasoningText`, `ProtectedReasoning`, `CachedUsage`, `JsonObject` (a bare JSON reply with no schema; where it is not claimed, a bot set to JSON-only is refused in words before anything is sent) and `PdfInput` (the model record says it reads PDFs, and a PDF goes on the wire as a document; checked both ways).

Each connection stores a **capability record per model**, in Drover's own shape: context size, maximum output, tool calling, vision, PDF input and the provider's PDF bounds, reasoning and its effort levels, structured output, built-in web search, price per million input and output tokens, privacy mode. The bot editor uses it to show only what a model can do, and cost tracking uses its prices. Providers that publish this are read automatically, and so are compatible servers that publish it in their model list or their model details ([What a model can do, and what it costs](#what-a-model-can-do-and-what-it-costs)). What no server reports, a space admin fills in, on any connection, and it survives every refresh.

### Images in requests

The one image a run sends today is a screenshot from the computer tools ([07-sandbox.md](07-sandbox.md#computer-use)). It crosses the boundary as `DataContent` in the agent framework, `ModelData` (bytes and media type) in Drover's transport, and, on the OpenAI-compatible wire that Venice shares, a user message whose content is a `text` part and an `image_url` part holding a `data:image/png;base64,...` URI, placed after the tool result, which stays text (`OpenAICompatibleTests.A_tools_picture_goes_out_as_an_image_url_data_uri_in_a_user_message_after_the_tool_result`). It is sent on one model call and never stored.

### Image generation

`image.create` is a built-in write tool. A bot sees it only after a person grants it and only where `AllowImageGeneration` permits it. The tool uses the bot's model connection, requires an image model name, and asks the connection's image adapter for one PNG. The compatible wire sends one bounded request to `images/generations` and accepts one bounded base64 PNG.

The generated bytes use the normal tenant-scoped file store. The file row carries the conversation's audience and the bot as creator, counts against the existing file limits, and becomes an image part of the reply that requested it. The tool call id is the file id, so a replay finds the existing file without generating or charging for another image. Provider-reported tokens and price become a normal usage record. A catalog's flat per-image USD price is recorded as a catalog estimate. Tiered image prices stay unpriced because this tool does not yet represent the provider's resolution and quality tiers. Any other provider that gives no reliable price also produces an unpriced usage record rather than a made-up zero.

**The vision gate.** The run engine offers the computer tools only when the bot's model has `Vision` in its catalog entry, or the bot has a screen reader set. Venice fills it from its model list (`supportsVision`); a generic compatible endpoint claims no vision until the operator marks the model, so a model that cannot look, with nothing to look for it, is not handed a screen.

**The screen reader's call.** A screen reader is another model of the space, chosen in the bot editor's Model section, whose catalog entry has `Vision`; it describes each screenshot so the bot's model gets words and never the picture ([07-sandbox.md](07-sandbox.md#computer-use)). `ScreenDescriber` (`Drover.Engine`) makes the call the way a run makes its own: it reads the connection, the catalog entry, the key, and the space's effective policy in a short tenant transaction, closes it, picks the `IModelClientProvider` for the connection's kind (so `ModelProviders` and every other provider the server does not register stay out), and calls `IModelChatClient.GetResponse` once inside `OutboundAttempt.Begin`, so `AllowPrivateAddresses` of the deployment and the space applies to it as to the bot's own calls. The request is `ModelChatOptions.Instructions` (Drover's fixed text, which the compatible transport sends as the system message: `OpenAICompatibleTests.A_screen_readers_request_goes_out_as_the_instruction_then_one_user_message_with_the_picture_and_no_tools`), one user message with text and a `ModelData` PNG, `MaxOutputTokens` 1000, no tools. It counts against the run's model calls (`MaxStepsPerRun` and `MaxTokensPerRun` as the run has them, through `BuiltinToolCall.BeginModelCall`; the count is held by the execution, so after a restart only the bot's own steps are counted again) and is bounded by `RunOptions.ScreenReadTimeout`. A provider failure is the tool's error in words; nothing falls back. No deployment rule was added: the reader is a model connection of the same space, called under every rule that binds the bot's own model, paid by the same space's key, and a screen exists only where `AllowDesktopSandboxes` allows one.

**Its usage.** The usage the reader reports is recorded against the run exactly as the run's own calls are (`RunGovernor`, through `BuiltinToolCall.RecordModelUsage`): a `usage_records` row with the run, the root run, and the bot, priced from the reader's catalog entry, a `usage.recorded` event at the current step, and the run's totals. The row's `model_connection_id` and `model` are the reader's, not the bot's, which is how a person tells the two apart; the event carries no model and was not changed. A picture a person attaches reaches the bot's own model, when its catalog entry says it reads images; the screen reader is not used for it ([02-data-model.md](02-data-model.md#sandboxes-files-secrets-audit)).

### Stored fallback chains

A bot keeps up to five ordered fallback models in `model_settings.fallbacks`. Each entry names a model connection and
model. `use_space_fallbacks` defaults to true, so a bot with no list of its own uses the space's
`settings.model_fallbacks` list unless it opts out. Saving a fallback requires a connection from the same space and a
catalog model whose state is not `missing`. The primary model and fallback entries cannot repeat.

`GET /api/spaces/{spaceId}/bots/{botId}/model-chain` describes the effective chain without running it. It returns the
primary model followed by the bot list or space list, with connection state, capabilities, token prices, privacy mode,
and plain sentences for capability mismatches. A stored entry whose connection no longer exists is skipped when the
chain is read. Runtime switching between entries belongs to the run engine, not the stored settings API.

## Venice, first-party

Venice is supported as a named provider with its own adapter, not as "a compatible endpoint that happens to work". Setup is: choose Venice, paste a key, done.

### What the adapter does

| Area | Design | Source fact |
| --- | --- | --- |
| Connection | Fixed base address. The setup screen asks only for the key. An inference key is all Drover needs; it never asks for an admin key. | Bearer key; two key types exist |
| Model discovery | Reads the public model list and traits. No key needed, so the model picker works before the key is saved. Refreshed daily and on demand. | The list endpoint is keyless and returns capabilities, context sizes, prices, privacy mode, and traits |
| Capability record | Filled from the list: tool calling, vision, reasoning with its effort options, structured output, web search, context and output limits, prices in dollars. | Fields exist per model |
| Defaults | The starter bot uses the provider's own "default" trait. Other traits (reasoning, code, vision, most capable) are offered as one-tap choices. | Traits endpoint |
| Chat | The OpenAI-compatible chat endpoint through the shared protocol transport in `Drover.Adapters.OpenAICompatible`. Streaming, tools, parallel tool calls, structured output, images. | "Any OpenAI SDK works" |
| Provider options | Sent with the documented model suffix form, `model:key=value&key=value`, so no custom request body is needed. | Documented suffix syntax |
| **System prompt** | The provider's own system prompt is switched **off** on every request. A Drover bot's instructions are fully the user's; nothing is prepended. | Default is on unless disabled |
| Reasoning | Reasoning text arrives in a non-standard field. The adapter maps it to Drover's `reasoning` message part. For models that return an encrypted placeholder, the part is marked "not available". Effort maps from the bot's provider-neutral `reasoning_effort`. | Field and placeholder documented |
| Built-in web search | A per-bot model setting: off, on, or automatic, with citations. Citations returned by the provider become source links on the message. This is separate from, and can be used alongside, Drover's own `IWebSearch` tool. | Three-state option; citations returned |
| Privacy mode | Each model's mode (private, anonymized, or attested) is shown as a badge in the model picker, in the provider's own terms, with a link to its explanation. A space setting can restrict bots to private or attested models only. | Published per model |
| Balance and limits | Response-specific balance headers are pre-request snapshots, not post-charge balances. Rate-limit headers drive backoff. A low-balance or limit error becomes a plain message on the run. | Headers documented |
| Cost | Calculated from token usage and the listed prices. Not read from billing, which needs an admin key. | Prices per model in the list |

### One key, several features

Venice also offers the other provider types Drover has interfaces for. The same connection lights them up, each as its own adapter class in the Venice project, each optional:

| Drover interface | Venice capability | Phase |
| --- | --- | --- |
| `IEmbeddingProvider` | Embeddings | 1, with memory |
| `IWebSearch` | Search endpoint (marked experimental by the provider) | 1 |
| `ITextToSpeech`, `ISpeechToText` | Speech and transcription | 2, with voice |
| Image generation tool | Image endpoints | 2 |

So a self-hoster with only a Venice key gets chat, memory, search, and later voice, with nothing else to configure.

### Not used, and why

| Item | Decision |
| --- | --- |
| The community .NET package for Venice | Small, unofficial. The surface Drover needs is the compatible chat endpoint plus a handful of simple calls; the adapter owns them. |
| The provider's client-side encrypted mode | It disables web search and some tool flows and needs client-side key handling. Worth a look in Phase 2 for bots that do not use tools. |
| The provider's own MCP server | It is a local process. Like every local-process server it runs only inside a sandbox, Phase 2. |
| Wallet-based key creation | Out of scope. The user brings a key. |

### Verification and remaining live gate

- **Offline behavior is pinned.** Recorded fixtures and deterministic generated responses cover whole/streamed text, tool round trips, structured output, reasoning, fragmented encrypted placeholders, citations on empty-choices stream chunks, response-isolated balances, safe retries, cancellation and sanitized failures. The SDK still owns the wire protocol.
- **Documented options.** The [suffix guide](https://docs.venice.ai/api-reference/endpoint/chat/model_feature_suffix) documents `include_venice_system_prompt=false`, `enable_web_search=on|auto`, `include_search_results_in_stream=true`, and `disable_thinking=true`. Search requests enable streaming search results so citations are available on metadata chunks. `reasoning_effort` remains a body field. Provider values `max` and `minimal`, which the framework enum lacks, are preserved through the OpenAI SDK's extensible request option inside the protocol adapter. Some mandatory-reasoning models may still compute and bill reasoning tokens when thinking output is disabled.
- **Documented metadata.** The [rate-limit guide](https://docs.venice.ai/api-reference/rate-limiting) uses Unix milliseconds. The adapter validates timestamp ranges and waits for the latest valid request/token reset, including the failed-request reset when present. The [response-header reference](https://docs.venice.ai/api-reference/api-spec#response-headers-reference) documents USD/DIEM balance headers as pre-request snapshots. The [reasoning guide](https://docs.venice.ai/guides/features/reasoning-models) documents `[Some reasoning content is encrypted]`.
- **Connection testing.** The documented `GET /api_keys/rate_limits` accepts inference or admin keys and does not make a billed model call. Drover asks only for an inference key.
- **Timeout ownership.** SDK retries and its separate network timeout are disabled. The named HTTP client's resilience pipeline owns retry/timeout policy; POSTs are not replayed after an ambiguous server error or timeout. A pipeline test verifies the resolved SDK timeout without waiting for it.
- **Keyed verification remains a gate.** Hand-written fixtures say so and never claim to be captures. Explicit `Live` tests are excluded from normal and PR runs. The owner must run the keyed tests before production wiring/deployment; no keyed inference was performed to validate this change. Public model/trait discovery is a separate, keyless test.

### Terms to read before the hosted service

Self-hosting with the user's own key raises no issue in the provider's terms. For a hosted service, the terms require that a product built on the API binds its own users to terms at least as protective, and their general license language speaks of personal use. The owner should read the current terms, and likely contact the provider, before offering Venice on the hosted service. This is listed in [12-risks.md](12-risks.md).

## OpenAI, on the Responses API

The `openai` kind connects OpenAI with an API key and nothing else. `OpenAIProvider` and `ResponsesChatClient` live in `Drover.Adapters.OpenAICompatible`, the one project that references the vendor package. Its address is fixed at `https://api.openai.com/v1/`: a connection carries none, and the connection's own address is never used. It has its own named client, `drover-openai`, with the same resilience rules as the compatible client and `SpaceOutboundHandler` added by `AddModelProvider`. A connection made with the compatible kind and OpenAI's address keeps chat completions; this kind is separate.

| What | How |
| --- | --- |
| Calls | `GET /v1/models` to list and test; `POST /v1/responses` for every model call, whole or streamed. The key goes as `Authorization: Bearer` |
| Nothing stored at the provider | Every request sends `store: false` and never `previous_response_id`: Drover owns the conversation and sends it whole in `input` each time. This is not a setting |
| Reasoning carried by Drover | With `store: false` each reasoning item comes back with `encrypted_content`, which arrives as `ModelReasoning.ProtectedData` and goes back unchanged as a reasoning item in the next call of the same tool loop. The item's id is not sent, because the provider keeps no item to look it up in. Reasoning held only as words (a stream's summary text, or reasoning text kept in a thread's history) is not sent back. `include` is not sent: a stateless request gets the encrypted content by default, and a model that does not reason refuses the include. Keeping protected reasoning in a thread's history between turns is #536 |
| Reasoning words | `reasoning.summary: "auto"` on every request, so `ModelReasoning.Text` has words. A model that does not reason accepts it and ignores it. When the provider answers 400 naming the summary (an organization not yet verified for summaries, or a model that refuses the setting), the same call is made once more without it, before anything is shown; any other 400, or a second refusal, is the call's failure. `reasoning.effort` is sent only when the bot or the call sets one, as given: the values each model takes differ, and the provider's own refusal says which |
| Other settings | `MaxOutputTokens` to `max_output_tokens`, `AllowMultipleToolCalls` to `parallel_tool_calls`, instructions to `instructions`, a schema to `text.format` (`json_schema`), the bot's JSON switch to `text.format` `json_object`. Function tools are flat (`type`, `name`, `description`, `parameters`); a call comes back as `function_call` and its result goes back as `function_call_output`, matched by `call_id` |
| Files | Pictures go as `input_image` parts. Any other file is refused in words before anything is sent; the engine gives a model other files as text. Native PDF input is a later change |
| Usage | `InputTokens`, `OutputTokens`, `CachedInputTokens` from `input_tokens_details.cached_tokens`, `ReasoningTokens` from `output_tokens_details.reasoning_tokens`; a count the provider does not send stays null |
| Endings | `status: "incomplete"` (or a `response.incomplete` event) ends as `length`, or `content_filter` when the provider says the filter cut it. A refusal part is the reply's text and ends as `content_filter`. A whole answer with `status: "failed"`, and a `response.failed` or `error` event in a stream, is a failure of the call, mapped by its code (`rate_limit_exceeded`, `slow_down` and `server_is_overloaded` to retry later, `insufficient_quota` to out of credit, `context_length_exceeded` to too long, `server_error` to unreachable, anything else rejected); the provider's message is not repeated, since it can quote the input |
| Failures over HTTP | As for the compatible client: 401 and 403 are an invalid key, 429 is retry later with the provider's `Retry-After`, `context_length_exceeded` is too long |

**In the connect form.** The client offers this kind from the server's list of kinds, after Venice, with the kind's name and key hint. The `gemini` kind connects Google Gemini with an API key and nothing else: the provider has no plan sign-in, so a key is the only way in. `GeminiProvider` and `GeminiChatClient` live in `Drover.Adapters.Gemini`. ## Generic compatible endpoints

One base address and an optional key covers most hosted providers and local model servers. The adapter lists models from the endpoint when it can and otherwise lets the operator type a model name. Capabilities default to "tools and streaming, nothing else claimed" until the server or a space admin says more, so a bot is never offered a feature the model lacks.

### What a model can do, and what it costs

A compatible endpoint is read before anyone is asked. `OpenAICompatibleProvider` reads each entry of the model list by its shape (`PublishedModelFacts`), with no host name checked:

- An entry in the shape a routing service publishes (`context_length`, `top_provider.max_completion_tokens`, `architecture.input_modalities`, `supported_parameters`, `pricing.prompt`, `pricing.completion`, `pricing.input_cache_read`) fills the context size, the longest answer, vision (`image` among the input modalities), tool calling, reasoning (with the effort levels `low`, `medium` and `high`, `ReasoningLevels.Documented`; the routing service maps a level a model does not support to the nearest one, and the local server treats a recognised level as "on" or falls back to the model's default, so neither refuses one a model lacks; each model's exact levels are not read) and structured output (from `supported_parameters`; a list that leaves out `tools` is read as a model that does not call tools) and the prices (strings of dollars per token, times 1,000,000; a negative or unparsable price stays unknown).
- A plain entry that carries `max_model_len`, as a server that serves one model does, fills the context size. No other context key is read, because none other is confirmed against a server's documentation.
- After any model list the adapter probes `POST {origin}/api/show` for the first model (the origin of the connection's address, through the same named HTTP client, so the space's private-address rule applies). A 200 answer with a `capabilities` array means a local server that keeps abilities apart from its list: the adapter then asks for the other models, four at a time, each bounded by `MaxModelListBytes`, the whole pass allowed two minutes from its first request (it starts after the model list has been read; the list call has its own timeout). `tools`, `vision` and `thinking` fill tool calling, vision and reasoning (`thinking` also fills the same effort levels), and the `model_info` key that ends in `.context_length` fills the context size. A refusal such as 404, or a 200 without `capabilities`, ends probing: a server that is not of that kind costs one extra request. A first probe that could not answer (a timeout, a reset, a 5xx, a rate limit, an answer that is not JSON) says nothing about the kind, so the models the list said nothing about are marked as not read and keep what is stored. A model the pass did not reach keeps what the list gave and is marked as not read (`ModelInfo.FactsRead`), so a refresh keeps what is already stored for it; the service tells the adapter which models are already filled (`ModelEndpoint.Filled`) and the adapter asks for the others first. Probing has no switch.

What no server reports, an admin says. Two nullable `jsonb` columns of `model_catalog` hold it apart from what the provider reported: `operator_capabilities` (`ModelCapabilityOverrides`: context size, longest answer, tool calling, vision, reasoning, effort levels, structured output, makes images, each nullable) and `operator_pricing` (`ModelPricing`). `ModelCatalogEntry.EffectiveCapabilities` and `EffectivePricing` lay the admin's values over the provider's, member by member (the admin's currency applies to the prices the admin set; a price the provider reported in another currency is not mixed in and becomes unknown), and every reader outside `CatalogUpsert` uses them (the bot editor's checks, the file and picture paths, `image.create`, the screen reader, the conversation model lists, the run's price and compaction size). `CatalogUpsert.Refresh` never writes the operator columns, so a refresh leaves an admin's values in effect and a member the admin clears falls back to the provider's value for that member only. `ModelCatalogResponse` carries the effective values and `operatorSet`, the names of the members an admin set (`contextSize`, `maxOutputSize`, `toolCalling`, `vision`, `reasoning`, `reasoningEfforts`, `structuredOutput`, `imageGeneration`, `inputPerMillion`, `outputPerMillion`, `cachedInputPerMillion`). A price an admin types is trusted for cost limits.

| Route | Who | What |
| --- | --- | --- |
| `PUT /{id}/model-settings` | admin | `{ model, capabilities?, pricing? }`. The request is the whole of what the admin says: a member left out or null is cleared. A model the catalog does not have is added as available, which is how an admin adds a model on a server that lists none; a connection that already holds `MaxModelsPerConnection` models takes no new row. Answers the catalog entry. The model is in the body because a routed model's ID holds slashes. |
| `DELETE /{id}/model-settings?model=` | admin | Clears both columns for the model; the row stays. 204. |

Both run in the space's tenant scope, take the row with `SELECT ... FOR UPDATE` once it exists (a refresh and an admin's change never put each other's value back); a model the catalog does not have is first inserted with `INSERT ... ON CONFLICT DO NOTHING`, so two requests that add the same model both succeed, and write an audit row, `model.settings_changed`, with the connection as target, the model, and each member that changed with its value before and after. Another space's connection is 404 and a member is 403. Sizes are whole numbers of 1 or more with no other bound; prices are 0 or more with at most six decimals; the currency is three letters; effort levels are from `minimal, low, medium, high, xhigh, max` and only with `reasoning` in effect. Each has its sentence (`ModelSettingsRules`). Effort levels follow the reasoning that is in effect: with it off, whether the admin's word or the provider's, the effective levels are none.

The older `PUT /{id}/models/vision` keeps its request and answers, for compatible endpoints only: it now writes `operator_capabilities.vision` (true to mark, null to clear). The migration moved every existing `VisionSetByOperator` mark into that column and took the flag out of `capabilities`. The `VoiceSetByOperator` marks are unchanged and live in `capabilities`. On the Models page, "Edit what this model can do" in each model row's menu (admins and owners) opens the sheet of [providers.md](../ux/providers.md) section 3; it opens filled with the effective values and sends only what was changed or already set.

### Named providers

A person who does not want to type an address picks a provider by name. A named provider is a starting point, not a kind: the stored kind stays `openai_compatible` and the connection keeps its `BaseUrl`, so every adapter lookup, the vision and voice marks and the speech and image paths work as they do for a hand-typed address. A provider whose address changes is fixed by editing one row of the connection, and a provider that needs its own wire gets its own kind.

The table is `KnownProviders` in `Drover.Adapters.OpenAICompatible`, one compiled-in list of `ModelProviderPreset` records (`Drover.Domain`): `Id`, `DisplayName`, `Address`, `KeyRule` (`Required`, `Optional`, `None`), `KeyPage` (https only, or null) and `Local` (the address is on the person's own machine or network). Nothing else in code repeats an address, and nothing at run time adds or changes a row: an address a server calls with a person's key is not taken from a file fetched over the network. The compatible kind's `ModelProviderDescriptor` carries the table as `NamedProviders`, and `GET /api/model-provider-kinds` (signed in) returns it with that kind, in table order, as `ModelProviderPresetResponse` rows. `ModelProviderCatalog.Offered` leaves out the `Local` rows where the deployment's `AllowPrivateAddresses` is false, and the whole kind (so its named providers) where `AllowedModelProviderKinds` does not offer it. **A named provider whose own kind is offered is not listed**: a row whose `Id` is a kind the server offers (today `openai`, the provider's Responses API, and `gemini`, the provider's own `generateContent` API) is left out, so one provider is never offered twice, and it comes back when the policy switches that kind off. The row stays in the table. Create is unchanged: the client sends `kind: openai_compatible`, the row's address and the key, and `ModelConnectionService` applies every check it applies to any address.

The forms that connect a model (setup, and Add a connection on Models) draw their provider choice and fields from `GET /api/model-provider-kinds` through `NamedProviders` in `Drover.Presentation`: each kind in the server's order, its named providers first, then the kind itself. Whether an address is asked for, whether a key is required, optional or not used, and both hints are the descriptor's. Up to four choices are a segmented control and five or more a list (and a list too when the segments, each as wide as its widest word, need more than the form column has: `SegmentedControl.MinimumWidth` against the column's width), a server with one kind and nothing named shows no choice, and a server that offers no kind shows "This server offers no model provider" in place of the form. While the kinds are read, and when they cannot be, the form is not drawn: a loading line, or the title "Drover could not load the providers" with the failure sentence and "Try again". Continue is allowed without a passing test and saves the connection as not tested. The client names no kind except the compatible one, which a named provider is a starting point for (`NativeInterfaceRuleTests.No_provider_kind_is_named_in_client_source`). A connection whose kind is not in the list shows an `Off` badge and the operator sentence.

The order is OpenAI, OpenRouter, Google Gemini, xAI, Groq, DeepSeek, Mistral, the other hosted providers by name, then the local ones. Each row's comment in `KnownProviders.cs` names the documentation page that confirmed its address on 2026-11-26. Key pages are confirmed for Groq, DeepSeek, Cerebras, Nebius and Together only. `KnownProvidersLiveTests` lists models on each row whose key is in the environment (`DROVER_TEST_KEY_{ID}`); it settles what a page cannot.

### Azure OpenAI

The model list of this provider describes its own models, not a resource's deployments, so the connection test on these hosts ends with "Type your deployment name as the model." Entra ID sign-in and the classic dated API are not supported. What a real resource answers (which key form it accepts, what its model list holds) is recorded by `AzureOpenAILiveTests`, which only the owner runs; until it has been run, this section does not claim that the bearer form alone is accepted.

## Decision models

A decision model answers typed questions about a state with probabilities and writes no text. Drover asks one to judge a bot rule written as a sentence ([03-run-lifecycle.md](03-run-lifecycle.md#rules), ADR 0026). `IDecisionModelProvider` (`Drover.Domain.Decisions`) turns an endpoint, a key and a model into an `IDecisionModel` and tests the connection. One adapter, `Drover.Adapters.SystemOne`, speaks the state-and-questions API that several providers serve, with `HttpClient` and `System.Text.Json` and no package. A kind is its address rule, its auth header, and its envelope; the request and the answer are the same for every kind. Each provider states, through `IDecisionModelProvider`, its name, its key rule (`ModelKeyRule`), and its address rule (`DecisionAddressRule`: `Fixed`, an `Address` a person gives, or an `Account` the address follows from), and `AddressFor` gives the address a connection's calls go to, so no code outside the adapter knows a provider's address.

The wire: `POST` with `{ model, state, questions }`. `state` is an object of the named texts Drover sends. `questions` is an object, keyed by name, of `{ type: "noul", instructions }` (yes or no) or `{ type: "choice", instructions, criteria: { label: description } }` (pick one). The answer is `{ model, answers, usage }`, `answers` keyed by the same names: a `noul` answer is `{ type: "noul", noul }`, the probability of yes from 0 to 1; a `choice` answer carries `choice`, `confidence`, and `probabilities` by label. `usage.input_tokens` is returned as usage. Questions go out under the adapter's own names (`q1`, `q2`, ...), which every provider accepts, and come back under the caller's. At most 64 questions go in one request, the lowest bound any provider states; more are sent as further requests, each with the whole state, and the caller sees one answer. A question the provider refused (OpenRouter's `{ type: "refusal" }`) or answered with something that is not a probability has no answer, which the caller treats as unreadable. An answer over 1 MiB is refused as it is read. An answer that is not this API is `Rejected` ("The server answered, but not in the decision model API Drover speaks."). Failures map through `ModelProviderException.FromStatus`; a private address the checked outbound handler refuses keeps the refusal's own words. There is no retry: the caller bounds a check's time (`MaxJudgedRuleSeconds`). `TestConnection` asks one fixed question with a known yes and answers `Connected. Answered in {n} ms.`, or the mapped failure.

The providers are registered by `AddDroverDecisionModels` (`Drover.Server`), which puts `SpaceOutboundHandler` on the adapter's one named client, `drover-decisions`. A space connects one, below.

### A space's decision model

Each space has at most one decision model connection (`decision_connections`, unique on `space_id`), connected by an owner or admin under `/api/spaces/{spaceId}/decision-model`. Antiforgery applies to every change.

## Voice

Speech has three jobs, each behind an interface Drover owns in `Drover.Domain/Voice`, and each chosen on its own:

| Interface | Job | Over the wire |
| --- | --- | --- |
| `ISpeechToText` | Write down a recording | `POST {base}/audio/transcriptions`, multipart, bounded by `MaxVoiceRecordingBytes` |
| `ITextToSpeech` | Read text aloud, streamed as it is made, and list a model's voices | `POST {base}/audio/speech`; `GET {base}/audio/voices` where the server has it |
| `IRealtimeVoice` | Hold a live call with a speech-to-speech model | One WebSocket at `{base}/realtime?model=`, or at `{base}/live/sessions` for a model that hands its work over |

One adapter serves all three for a compatible connection (`OpenAICompatibleProvider`), so a provider works when its address does. No package was added: the adapter speaks the protocol with `HttpClient` and `ClientWebSocket`, through the same checked outbound handler as every other provider call, with the space's private-address rule on each request.

| Provider | Base address | Listens | Speaks | Live calls |
| --- | --- | --- | --- | --- |
| OpenAI | `https://api.openai.com/v1` | yes | yes | yes |
| Groq | `https://api.groq.com/openai/v1` | yes | yes: 200 characters a request and WAV only, which Drover handles (below) | no |
| xAI | `https://api.x.ai/v1` | no | no | yes. Its own speech and transcription endpoints are not this shape |
| Ollama | `http://host:11434/v1` | where the model does | where the model does | no |
| Kokoro-FastAPI | `http://host:8880/v1` | no | yes | no |
| Speaches | `http://host:8000/v1` | yes | yes | no |

Anthropic has no speech API, so a space whose bots answer with its models still names another connection, or the server's own speech service, for voice.

**Which models do what.** A compatible endpoint lists model names and nothing about them, so the adapter marks a model from its name when the catalog is refreshed (`KnownVoices.Mark`): names with `whisper`, `transcribe`, `stt` or `parakeet` listen; names with `tts`, `kokoro` or `orpheus` speak; names with `realtime`, or that begin `grok-voice` or `gpt-live` (but not `gpt-live-transcribe`, which listens), hold live calls. A `gpt-live` model only holds the conversation and hands its work to the bot's run ([03-run-lifecycle.md](03-run-lifecycle.md#a-model-that-hands-its-work-over)). An unknown name gets no mark. A space admin sets or corrects the three marks for one model with `PUT /api/spaces/{space}/model-connections/{connection}/models/voice` (body `{ model, speechToText, textToSpeech, realtimeVoice }`, compatible connections only, admin only). A mark set by hand is kept across refreshes (`VoiceSetByOperator`); all three false clears it.

**Which model a space uses.** `spaces.settings.voice` holds up to three choices, `listen`, `speak` and `live`, each a connection, a model and optionally a voice (`PUT .../voice/settings`, admin only; a connection of another space or a model not marked for the slot is refused with a sentence). A slot left empty is chosen by the server (`VoiceChoices.Resolve`): the first connection by name that has not failed and has an available model with the mark, the first such model by name, and the first voice the adapter lists. If the space has none, the server's own speech service is used. `GET .../voice/options` returns what each slot can use, what it uses now, whether that was chosen automatically, whether its address reads as one on a private network, and the three limits.

**The server's own speech service.** An operator may name a compatible speech endpoint for the whole server: `Drover:Voice:Speech:BaseUrl` (with `:Model`, default `kokoro`, and `:Voice`, default `af_heart`) reads aloud, and `Drover:Voice:Transcription:BaseUrl` (with `:Model`, required) writes down recordings. `compose.voice.yaml` runs a speech container beside Drover and sets the first, so read aloud works with nothing to set up. It appears in every space's options as "This server" with no connection id, is used only when the space has no model of its own for the slot, and holds no live calls. Its adapter (`OperatorSpeech`, kind `server_speech`) is the same protocol on a client of its own that follows no redirect and marks each request as going to an operator-configured address (`OperatorAddressHandler`), exactly as the search service does ([16-deployment-policies.md](16-deployment-policies.md)). Because the address is the operator's own, it is reached on a private address even where `AllowPrivateAddresses` is off, so the speech container beside the server works on a hosted server and on one with open registration. No space, person or bot can create a connection of that kind or change where it points. A value that is not an http or https address, or a transcription address with no model, stops the server and names the setting.

**The endpoints** are under `/api/spaces/{space}/voice`, open to members, and sit outside the tenant scope filter because each waits on a provider. `VoiceService` opens short transactions of its own as the person who asked (read the choice, reveal the key, work out the space's outbound rule; close), calls the adapter under `OutboundAttempt.Begin`, and never holds a transaction across the wait.

- `POST /transcribe` takes the recording as the raw body with its `Content-Type` (`audio/webm`, `audio/wav`, `audio/mp4`, `audio/mpeg`, `audio/ogg`) and answers `{ text }`. A body declared larger than `MaxVoiceRecordingBytes` is refused before any of it is read, and one sent without a length is cut off at the same limit while it is read; both answer 413 with a sentence. The audio goes from the request to the provider through memory. It is never written to disk, to the database or to a log, and neither are its words.
- `POST /speak` takes `{ messageId }` or `{ text }` (a sample of a voice), never both, with an optional `voice` and `format` (`mp3` by default, `wav`, `opus`, `pcm`). A message is read inside a transaction as the caller, so row-level security decides whether they may: a message of another space or of another member's private conversation is 404. Only its text parts are spoken, never reasoning, tool calls or tool results. Text past `MaxReadAloudCharacters` is refused with a sentence. The audio is streamed as the provider makes it, with the format's media type; nothing is sent until the first of it arrives, so a provider that refuses is still answered with a problem.
- Long text is cut into pieces a provider takes in one request (`SpeechText.Split`): at the end of a sentence where it can, at a space where it cannot. A piece is 4,000 characters, or 200 for `api.groq.com`, and the pieces are asked for in order. Several pieces are asked for as MP3 whatever was requested, because MP3 answers play when put end to end and other containers do not. `api.groq.com` answers only in WAV, so it is always asked for WAV, and its answers are joined (`WavJoin`): the first 44-byte header is kept with both lengths set to `0xFFFFFFFF` (unknown, as a stream's are) and the header of each later answer is dropped.
- A provider failure (`ModelProviderException`) answers 502 with the adapter's own sentence, never the provider's text. Nothing set up for the slot answers 409 with what to do: "Reading aloud needs a speech model. Connect one under Models."

**Usage is not recorded yet.** Usage rows belong to runs (`runs.usage`), and transcription, read aloud and calls happen outside any run, so today the server logs ids, byte and character counts, durations and a call's token counts, and stores no cost. Recording speech usage needs a place for usage that has no run, which is its own change.

Live calls are described in [03-run-lifecycle.md](03-run-lifecycle.md#live-calls).

## Signing in with a subscription

A person signs in to a model provider with their own account, and Drover uses that account in place of an API key. The token set is always the signing-in person's own, never a space credential ([ADR 0006](../adr/0006-credentials-belong-to-users-or-spaces.md)). The server side (issue #526, layer 1), the ChatGPT plan, the Claude plan ([below](#claude-plan-for-self-hosted-servers)) and the connect screen on the desktop head (layers 2 and 3) are built; the other providers follow, one at a time.

### Shape

| Part | What it is |
| --- | --- |
| `IModelSignIn` (`Drover.Domain/Models`) | One per sign-in kind, in that provider's adapter project. A kind is a sign-in kind because one is registered for it; no column says so. It names the kind, what a person calls it (the name of the connection it makes), whether it uses a personal paid plan, which return address the device may use (the configured one, where only the port may vary), and does `Begin`, `Finish`, `Refresh` and `Revoke`. `Refresh` throws `SignInEndedException` when the provider says the sign-in is over and `ModelProviderException` for anything that may pass. `Finish` throws `ModelSignInRefusedException` for a refusal or a return that is not the attempt's; nothing is exchanged then. No message holds a token. |
| `ModelSignInConformance` (`tests/Drover.Adapters.Conformance/Models`) | What every sign-in must do: PKCE (`S256`) with the attempt's own fresh state, nothing exchanged for a wrong state or a refusal, a refresh token never sent twice, each "over" answer and only those end a sign-in, no token in an exception. For a kind whose rig gives a pasted approval, a device that cannot listen is sent to a page with the same challenge and state and waits on `paste`, a pasted approval is exchanged once with the verifier, and another attempt's code or nothing pasted is refused with nothing exchanged. It runs against the in-memory reference provider the engine and API tests use. A sign-in whose credential is a key with no refresh token and no end (OpenRouter) sets `RefreshesTokens` false: its refresh must then return the current set and ask the provider nothing, and the rotation and ended-answer cases do not apply. `ModelSignInPollConformance` holds the polling flow's cases: a code, an https page, an interval and a lifetime of at most 15 minutes; null while pending; one exchange on approval; a refusal ends it; and the same refresh rules. |
| `model_connection_credentials` | One row per connection and person, always one person's ([02-data-model.md](02-data-model.md#tools-and-connections)). The token set (access token, refresh token, expiry, scopes, account label, and what the provider needs to sign in again) is one JSON value in the vault as `oauth_tokens`, private to that person. |
| `ModelSignIns` (`Drover.Engine/Models`) | Starts and finishes attempts. A pending attempt (PKCE verifier, state, nonce, person, space, kind, return address) lives in memory for 10 minutes, one per person and kind in a space; starting another ends the first. Only the person who started it, in the same space, can finish or read it; anyone else gets 404. On finish the exchange runs on the server with no transaction open, the token set is stored as a new secret (a person who signs in again gets a new one and the old one is deleted), the space's one connection of the kind is made if there is none (named for the kind, `ready`), and its models are listed once, as a refresh lists them. |
| `ModelCredentials` (`Drover.Engine/Models`) | The one place that decides what a model call sends. A key connection sends its key. A sign-in connection sends the access token of the person the call acts for, read inside that person's tenant transaction: the run's `principal_user_id` (the person talking, the owner of a routine, or for a delegated run its parent's person), or the person making a request. A person with no sign-in has no credential; there is no fallback to another person's sign-in or a key. Every model call goes through it: runs (`RunExecutor`), conversation summaries, the screen reader, image generation, connection tests and refreshes, and voice (which serves key connections only). |
| `ModelSignInRenewal` and `ModelSignInRenewer` | Once an hour, renew active sign-ins with an end that no call has renewed for seven days, found through `sys.model_sign_ins_due` (ids only) and each renewed in its own space as its own person. At most 50 a pass. Each one taken up is noted (`renew_attempted_at`) before anything else, and a renewal clears the note; one taken up and not renewed, because it failed or its kind is refused here, waits a day, so those cannot fill every pass. |

### Renewing

A call whose access token runs out within five minutes renews it first, after its read transaction has closed and been disposed. A run checks again before every model call (`RenewingChatClient`), so a token that runs out while a run goes on is renewed before the next call, and every token a run is handed is added to its redactor. It takes the credential's refresh lock, a session advisory lock on a connection of its own that reads and writes no row, so the provider is asked with no tenant transaction open; reads the row again in a short transaction (another call may have renewed it already, and then its tokens are used); asks the provider; and writes the new set with `ISecretVault.Replace` in another short transaction before letting go. Two runs that find the token running out make one refresh between them. A refresh whose answer says the sign-in is over marks the row `needs_sign_in` and keeps it; the run stops before any model call with `sign_in_ended`. Anything else (a network failure, a 5xx) leaves the credential as it was, and the call fails as `unreachable`. If the person signed in again while the provider answered, the new sign-in's tokens stand. Once the provider has answered a refresh or an exchange, the tokens are stored whatever happens to the call that asked (a stopped run, a closed request), because the old refresh token or the one-time code is already spent. Signing out holds the same refresh lock while it tells the provider and changes the row, so no renewal in flight can leave new tokens behind.

A run on a sign-in connection whose person has not signed in stops before any model call with `sign_in_required` and a sentence naming the bot and the connection.

### Routes

| Route | Request | Response |
| --- | --- | --- |
| `POST /sign-in` | `{ kind, redirectUri }` | `{ attemptId, address, wait }`: `wait` is `return` (the device receives the browser's return) or `paste` (the provider's page shows a code the person pastes). An unknown kind or a return address the kind does not take is 400, and so is none (a device with no listener) for a kind with no `paste` flow, unless the kind can return to the server (OpenRouter) and the server has an `https` public address. A refused kind is 403 with the rule's sentence. |
| `POST /sign-in/{attemptId}/finish` | `{ query }`: the query string the device received, or what the person pasted, at most 8 KB | The connection's summary. A refusal, a return that is not the attempt's, or an attempt that ran out is 400 with a sentence, and the attempt is over. |
| `GET /sign-in/{attemptId}` | none | `{ status, connection }`: `waiting`, `done`, `refused` or `expired`, and the connection once it is done |
| `DELETE /{connectionId}/sign-in` | none | 204, with no confirmation. Tells the provider where it can be told, then drops every token. What the provider registered for the person (`Details`, such as an issued client id) stays, with no token and no account label, in a row marked `needs_sign_in` that the caller's summary calls `signed_out`; a row that already holds no token, or kept nothing, is deleted with its secret. 404 when the caller has no sign-in to it. |

Each waits on the provider, so none sits under the tenant scope filter; the services open short scopes as the caller. `FinishModelSignInRequest` carries a one-time code and prints nothing of it.

### Who may sign in where

A sign-in kind is a provider kind too: its `IModelClientProvider` registers through `AddModelProvider` with a descriptor like any other, and the provider catalog decides first. A sign-in kind with no provider in the catalog, or one the deployment does not offer (`ModelProviders`, `AllowedModelProviderKinds`), is refused on every route, every use and the renewal with the catalog's sentence, before anything is sent. The deployment rule `SubscriptionSignIn` ([16-deployment-policies.md](16-deployment-policies.md)) is `Available` on a self-hosted server: every sign-in kind is on with nothing to set. Under the hosted preset it is `OnlyWithOperatorApproval`: every route and every use refuses a kind that uses a personal plan with "Signing in with a personal plan is not available on this server. You can add an API key instead.", before any request leaves; a flow the provider offers to any app stays on. Signing out is never refused: it deletes the person's own tokens and, for a refused kind, sends nothing. The operator's `Drover:Models:SignInOff` (a list of kinds, empty by default) switches a kind off the same way on any server, without a release.

### OpenRouter sign-in

`OpenRouterSignIn` and `OpenRouterProvider` (`Drover.Adapters.OpenAICompatible`), kind `openrouter_signin`, on the provider's documented flow (https://openrouter.ai/docs/use-cases/oauth-pkce, read 2026-11-27): the person goes to `https://openrouter.ai/auth` with `callback_url`, an S256 `code_challenge` and Drover's `state` (which the page returns unchanged), and the exchange `POST https://openrouter.ai/api/v1/auth/keys` with `{ code, code_verifier, code_challenge_method }` answers a `key` that belongs to the person. There is no registration, no client id and no client secret. It is not a personal plan (`IsPersonalPlan` is false), so the hosted preset keeps it on; `Drover:Models:SignInOff` can still switch it off.

- **No refresh, and no end unless the person or the provider ends it.** The authorize address sends `expiration=never` (the page lists it as a prefill the person can still change), so the key goes to the vault as a token set with no refresh token and no expiry. `Refresh` returns the set it was given and asks the provider nothing; `expires_at` is null, so the hourly renewal, which only takes up sign-ins with an end, never takes it up. `Revoke` returns, because no call a key can make ends itself; signing out deletes the secret and the row. `account_label` is null: the exchange names no account the page documents. A key can still be deleted, or given an expiry by the person, so a call with a key that has no end that the provider refuses with a 401 (not a 403, which the provider also answers for a blocked or moderated request) is the provider saying the sign-in is over: the credential is marked `needs_sign_in` (only if it still holds the token set the call was made with) and the run fails with `sign_in_ended`, not "check the key" (`RenewingChatClient`, `ModelCredentials.EndAfterRejection`). A sign-in with an end is left to its renewal.
- **Runs** use the same chat protocol and address as an OpenRouter connection made with a pasted key, with the key as the bearer. The provider's address is the kind's setting, never the connection's.
- **Return.** On a head that listens, the callback is the device's loopback address, sent as `localhost` (the page documents localhost callbacks on any port). On a head that cannot listen, and where the server has an `https` public address (`DROVER_PUBLIC_URL`), the callback is the server's own: `GET /api/model-sign-in/return/{attemptId}`. That route has no signed-in person. The attempt id is its only secret, so it is 128 random bits (every attempt id is now: 16 random bytes, not a version-stamped guid); the provider's `state` is still checked; it ends one attempt that is still waiting and was started to return there, once; any other id is 404. A leaked attempt id can cancel an attempt (a return with a wrong state ends it) but not take it over: the code is bound to the starter's PKCE verifier and the key goes to the starter's own row. A browser that carries a Drover session of someone other than the starter is refused with no exchange (the attempt stays for its owner). **Residual risk, as #526 step 12 specifies it:** the route takes anyone without a session, so a person who is tricked into approving a link an attacker started (the address is the attacker's attempt) completes the attacker's attempt, and the attacker's account then holds the key of the victim's OpenRouter account. The attacker must be a member of the space with a live attempt, the key stays private to the attacker's own sign-in row, and the victim's own consent page names the app and its key label; the provider's `state` and PKCE bind the code to the attempt, not to a browser. A kind with no such residual risk would need the head to carry the return, which a head with no listener cannot do. It answers a page of Drover's own words ("Signed in. You can close this tab.") and the head reads `GET /sign-in/{attemptId}`. With neither a listener nor an `https` address, the kind cannot start and the connect screen offers "Add a key".
- **Settings**, `Drover:Models:SignIn:openrouter_signin`, read on every request: `AuthorizeAddress` (`https://openrouter.ai/auth`), `TokenAddress` (`https://openrouter.ai/api/v1/auth/keys`), `RedirectUri` (`http://localhost:1455/auth/callback`, only the port varies), `ApiAddress` (`https://openrouter.ai/api/v1/`) and `KeyLabel` (`Drover`, prefilled as the key's label).
- **Unconfirmed.** Whether `127.0.0.1` is also accepted as a callback host (the page names `localhost`, which is what is sent), and whether `state` survives a callback address that carries a path (the server's own). `OpenRouterSignInLiveTests` settles both with the owner's account.

### ChatGPT plan

The kind `openai_signin`: `OpenAIPlanProvider` and `OpenAIPlanSignIn` in `Drover.Adapters.OpenAICompatible`, on the flow the provider documents for open source and locally hosted apps (https://developers.openai.com/siwc/token-sharing-open-source and its pages, read 2026-11-27 from the export https://developers.openai.com/siwc/llms-full.txt, and the discovery document https://auth.openai.com/.well-known/openid-configuration). Every address, scope and name is a setting under `Drover:Models:SignIn:openai_signin` (`OpenAIPlanOptions`), read for each request, so following a change at the provider needs no release.

| Step | What Drover does |
| --- | --- |
| Approve | The browser goes to `https://auth.openai.com/api/accounts/authorize` with `client_id=dynamic_agent_client` and `agent_name_hint=Drover` on a person's first sign-in, or the client id the provider issued to them on a later one; `ext_agent_host_id`, `response_type=code`, the device's `redirect_uri` (`http://127.0.0.1:<port>/auth/callback`, only the port may vary), the identity and plan scopes, `resource=https://api.openai.com/v1`, a fresh `state` and `nonce`, and an `S256` PKCE challenge. No client secret exists. |
| Return | The device hands the query string to `/finish`. A wrong or repeated `state`, an `error`, a first registration that comes back without an issued client id, or a later one that names another client id, is refused and nothing is exchanged. |
| Exchange | On the server: `POST https://auth.openai.com/api/accounts/oauth/token`, form encoded, with the issued client id, the code, the verifier, the same `redirect_uri` and `resource`. The ID token must pass the platform's token handler against the provider's published keys (RS256 only, issuer, audience is the issued client id, expiry) with the attempt's nonce; an answer without one is refused. A later sign-in must be the same account (`sub`), or it is refused with "That is a different ChatGPT account. Sign out first." Then the plan scope: an answer whose `scope` does not grant `chatgpt.tokens.use.direct` (an answer with no `scope` counts as not granting it) is told "ChatGPT signed you in but did not allow plan use. Try again and allow it." Any refusal after the exchange revokes the refresh token it issued, as a courtesy that logs only the kind of a failure. The token set keeps the issued client id, the host id and the subject in `Details`, and the email as the account label. |
| Kept between sign-ins | The provider asks the app to keep a person's registration: "Later sign-ins reuse the saved client ID", "Sign out: ... Retain its account/client mapping and this host's ID for a later sign-in" ("Accounts and sessions"), and for a sign-in without plan use "retain the sign-in but mark ChatGPT plan usage as disabled" and repeat OAuth "with the saved client ID and the complete requested scope set" and `prompt=consent` ("Errors and recovery"). So signing out, and a sign-in that did not allow plan use, keep the row as `needs_sign_in` with no account label and a token set that holds no token, only the issued client id, host id and subject (and, for the second, that plan use is not allowed, which adds `prompt=consent` to the next approval). The caller's summary reads `signed_out`, and a call through it is told to sign in, as for no sign-in. A sign-in that did not allow plan use is kept only on the space's connection of the kind when there is one, and never makes it; when it lands on top of a sign-in the person had, that one's tokens are revoked with the provider first, as a courtesy, under the refresh lock. Signing out of a row that holds no token removes the row and its secret, so signing out twice takes everything off the server. This differs from #526 steps 6 and 8, which delete the row on sign-out and keep nothing of a refused grant: the provider's pages are followed, because a new registration on every sign-in is what they ask apps not to make. |
| Host id | The provider asks for a stable, opaque `ext_agent_host_id` per host and leaves what a host is to the app. Drover counts each person's sign-in on a server as one host: a `urn:uuid:` made once, kept in the token set and sent again on every later sign-in, so it never names the person. A person who signs out and back in is a new host. |
| Refresh | Form `grant_type=refresh_token`, the issued client id, the refresh token and `resource`, no `scope`. Refresh tokens rotate (30 days), access tokens last an hour. `invalid_grant`, `invalid_refresh_token`, `token_expired` and any `refresh_token_*` code end the sign-in; anything else may pass. No request of the sign-in is retried. |
| Sign out | `POST https://auth.openai.com/api/accounts/oauth/revoke` (the discovery document's `revocation_endpoint`) with the refresh token, `token_type_hint=refresh_token` and the issued client id. |
| Runs | #528's `ResponsesChatClient` under its plan rules: only `GET /v1/models` and `POST /v1/responses` on the API address, the person's access token as the bearer. Every call streams (a whole answer is the stream put together) and `PlanRequestShaping` shapes each body: `store: false`, `stream: true`, no system-role item (their words go to `instructions`), none of the fields the plan refuses (`background`, `conversation`, `max_output_tokens`, `max_tool_calls`, `metadata`, `moderation`, `multi_agent`, `prompt`, `prompt_cache_retention`, `safety_identifier`, `temperature`, `top_logprobs`, `top_p`, `truncation`, `user`, `previous_response_id`), and function tools grouped in one namespace, `drover`, with each function call sent back naming it. A call the plan limited is not sent again. |
| Models | The plan's own list, `{"models":[{slug, display_name, visibility}]}`: entries whose `visibility` is `list`, in the provider's order, with no price. Each starts with tools, streaming, pictures, structured output and reasoning, and claims no image generation, web search or speech, so the bot editor does not offer them. |
| Failures | `subscription_sharing_usage_limit_exceeded` (429, or inside a stream as `response.failed`) is out of credit with "Your ChatGPT plan has reached its limit for now." and no time to try again; `subscription_sharing_user_not_eligible` (403) is a refusal, not retried and not a reason to sign in again; `subscription_sharing_usage_unavailable` and `subscription_sharing_user_unavailable` (503) are retry later; `subscription_sharing_unsupported_capability`, `subscription_sharing_route_not_supported` and the two `chatpass_v2_*` permission codes are refusals in words; `subscription_sharing_invalid_user` (401) asks the person to sign in again. A stream that closes before `response.completed`, `response.incomplete` or `response.failed` is a failure of the call, never a short reply ("Treat inference as successful only after receiving response.completed"). The provider's own message is never repeated. |

The return is a loopback address on the machine with the browser, so the browser flow finishes on a device that can listen there: the desktop app. The server makes the exchange and owns every refresh from then on, which matches the provider's guidance for a tool on a remote machine.

**Sign-in by code (layer 5).** A device that cannot listen (a phone, a browser tab) starts the sign-in with no return address, and the kind answers how it finishes there; the person never chooses. The waits are `return` (the device's listener, or the server's own return route), `paste` (the provider's page shows a code; the device posts it to `/finish`; one that does not work can be pasted again, at most five times per attempt) and `poll` (the device shows `code` from the start answer; `ModelSignIns` asks the provider in the background at the provider's interval, never sooner, five seconds longer after a slow-down, through failures that may pass, until approved, refused, replaced by a later attempt or the code runs out, 15 minutes at most; `/finish` is refused for it and the device reads `GET /sign-in/{attemptId}` every 2 seconds, whose answer carries Drover's sentence when it ended without a sign-in). The adapter keeps what it needs between start and finish (a device code) in `ModelSignInStep.Kept`, held in the server's attempt and never sent to the device. A kind names its loopback return address on the kinds route (`SignInReturn`), so the desktop listener keeps that host and path and asks for that port.

`openai_signin` has both flows under one kind and one connection: the browser flow where `redirectUri` is set, the code flow where it is null, with every value under `Drover:Models:SignIn:openai_signin:Code` (`OpenAIPlanCodeOptions`). The code flow is the provider's own command line tool's, read from that tool's published source on 2026-11-27: `POST https://auth.openai.com/api/accounts/deviceauth/usercode` (JSON `client_id`) gives `device_auth_id`, `user_code` and `interval`; the person enters the code at `https://auth.openai.com/codex/device`; `POST .../deviceauth/token` (JSON) answers 403 or 404 until approved, then an authorization code and verifier exchanged once at `https://auth.openai.com/oauth/token` (form, `redirect_uri=https://auth.openai.com/deviceauth/callback`). Refresh is JSON at the same address and rotates; sign-out revokes as JSON at `https://auth.openai.com/oauth/revoke`. The token set records `flow: code` and the account the access token's `https://api.openai.com/auth` claim names (`chatgpt_account_id`); what a browser sign-in registered is kept beside it. A refresh for another account ends the sign-in. The flow travels with each call in `ModelEndpoint.SignInDetails` (from `ModelCredential.Details`), so `OpenAIPlanProvider` sends that person's runs to `https://chatgpt.com/backend-api/codex/responses` and lists models at `.../codex/models?client_version=<ClientVersion>`, with `originator`, `OpenAI-Beta`, `accept` and `chatgpt-account-id`, `include: ["reasoning.encrypted_content"]`, `instructions` always present and tools not grouped. `usage_limit_reached` and `usage_not_included` (in `error.type` on a 429, or in a stream) are out of credit; any other 429 is retry later. A start the provider refuses says "ChatGPT refused the code. Turn on device code sign-in in ChatGPT's security settings, then try again."

**On the connect screen** (`ModelSignInFlow` in `Drover.Presentation`, `IModelSignInListener` in `Drover.Presentation/Platform`, `DesktopModelSignInListener` on the desktop head) a sign-in kind is one more entry in the provider list. Choosing it shows one line and one button, "Continue with {SignInName}". The desktop head listens on `127.0.0.1` (port 1455 if free, else any free port) at `/auth/callback`, starts the sign-in, opens the page in the system browser, and takes the first request on that path that names a `state` and a `code` or an `error` (anything else is answered 404 and it keeps waiting). It answers with "You can close this tab. Drover is finishing the sign-in." (it does not say signed in: the server has not finished), hands the query string to the server (which takes at most 8 KB) and stops listening. The states and their sentences are in [docs/ux/providers.md](../ux/providers.md). On Models, a sign-in connection's card says the caller's own sign-in only ("Using ChatGPT plan" with their account, ended, or not made), with "Manage usage" (the provider's usage page) while it is in use, "Sign in again" or "Continue with" otherwise, and "Sign out" in its More menu.

### Claude plan, for self-hosted servers

`AnthropicPlanSignIn` and `AnthropicPlanProvider` in `Drover.Adapters.Anthropic`, kind `anthropic_signin`, connection name "Claude plan" (#526 layer 6). The provider documents no sign-in for other apps and its terms forbid this use; the owner decided on 2026-11-26 to build it as #526 specifies, as a risk the operator accepts by leaving the kind on. The flow borrows the client identifier, addresses, scopes, headers and system prefix of the provider's own command line tool. Every literal value is a setting under `Drover:Models:SignIn:anthropic_signin` (`AnthropicPlanSignInOptions`, read for each request, so a change needs no release or restart), checked on 2026-11-27 against a working open source client.

| Aspect | Design |
| --- | --- |
| Sign-in flow | Authorization code with PKCE (`S256`) and Drover's own random `state`, never the verifier, at `StartAddress` with `code=true`. A device that listens gets the browser's return at `RedirectUri` (`http://localhost:<port>/callback`, any loopback host and port; the address sent names `localhost` on the device's port, which reaches a listener on `127.0.0.1` such as the desktop app's) and waits on `return`. Any other device is sent to `CodePageRedirectUri`, the provider's page that shows `code#state` to copy, and waits on `paste`. |
| Finishing | `/finish` takes `code#state`, a bare code, a whole return address, or a return's query string, up to 4 KB (`MaxPastedBytes`; longer is refused before it is read, and the endpoint takes at most `RequestLimits.Account`). A state that is not the attempt's is refused, and so is a browser return that names none. The exchange is JSON at `TokenAddress` (a relative `TokenAddress` is reported as a setting to correct, not as a provider answer): `grant_type`, `client_id`, `code`, `state`, `redirect_uri` (the same address the start named), `code_verifier`. A 4xx answer other than 408 and 429 is a refusal. |
| Tokens | Access tokens carry `expires_in`; refresh is JSON (`grant_type`, `client_id`, `refresh_token`) and rotates. A refresh answer with no refresh token keeps the stored one, and the next refresh sends it again; if the provider has ended it, that refresh's `invalid_grant` ends the sign-in. A refresh keeps the account label and details. A 400, 401 or 403 that names `invalid_grant` or a `refresh_token_` code, as an OAuth `error` string or as the `type` of an `error` object, ends the sign-in; anything else may pass. The account label is null. No revoke call is known: signing out deletes the token set and the row. |
| Runs | The key kind's Messages client and fixed address, with the person's access token as the bearer credential and no `x-api-key`, the configured `Headers` (`anthropic-beta`, `user-agent`, `x-app`) on every call and model list, and `SystemPrefix` as the first system block with the bot's instructions as the second. Models are listed from the provider's model list with the same headers. |
| Who | Each person signs in with their own plan; the hosted preset refuses the kind (`SubscriptionSignIn`), and `Drover:Models:SignInOff` switches it off on any server. |

Not confirmed by any working source, and left to the owner's `Live` test (`AnthropicPlanLiveTests`): whether the provider accepts a `state` that is not the verifier, whether its model list answers a plan token, and whether it serves tool names of Drover's own spelling.
